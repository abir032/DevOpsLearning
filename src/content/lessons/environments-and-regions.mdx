      - t: Nothing; Terraform tells environments apart by folder name

<Part id="problem">

<Story who="QuickCart, dev becomes three">

Maya built QuickCart's dev network with Terraform, in one folder. It needed a staging copy, so Leo copied the folder to `stg`, changed the address range, and ran `terraform plan`.

The plan said **8 to add, 1 to change, 6 to destroy**. It wanted to replace a VPC that stg didn't have yet. The copied folder still had dev's `backend.tf`, with dev's state key. Leo's "stg" was reading dev's memory, and planning to turn dev into stg. He read the plan, stopped, and fixed the key.

Six months later, QuickCart opened in Ireland. "The region is just a variable," they said. The apply failed half-way: the VPC was built in eu-west-1, and the first subnet was refused. Someone, long ago, had typed `us-east-1a` into the code.

</Story>

Both problems come from the same place: the difference between environments lived in more places than anyone could see.

<Case title="A very common mistake">

A team keeps dev and prod as two **workspaces** of one Terraform folder. An engineer switches to prod to check something, then carries on with dev work an hour later, forgetting to switch back. The folder, the files and the commands look the same in both workspaces. The plan shows changes that look like the dev experiment they expected, and they apply it to production. Nothing on the screen said which environment they were in.

</Case>

This lesson is about keeping environments apart in a way you can see, making them differ only where you choose, and reaching a second region without surprises.

</Part>

<Part id="idea">

An environment is a complete copy of QuickCart's infrastructure: **dev** for trying things, **stg** for checking a release, **prod** for customers. They should be built from **the same code**, so that what you tested in stg is what runs in prod.

So there are only two things that may differ between environments:

| What differs | Why | Where it lives |
|---|---|---|
| **The values** | stg may use three zones where dev uses two, and each environment needs its own address range | `terraform.tfvars` |
| **The state** | Each environment's resources must be remembered separately, or one environment's apply can change another | `backend.tf`: a different `key` |

<Key>Environments differ only in their values and their state key; the code is the same file everywhere.</Key>

### One folder per environment

Each environment gets a small root module of its own. All of them call the same child module:

```text title="Layout"
quickcart-envs/
  modules/
    network/            the shared code: one copy only
  envs/
    dev/
      main.tf           the same in every folder
      variables.tf      the same in every folder
      backend.tf        differs: the state key
      terraform.tfvars  differs: the values
    stg/                the same four files
```

To work on an environment you `cd` into its folder. The folder name is in your prompt, your shell history and your terminal's title. You can see where you are.

Here's dev's folder, file by file. First, `main.tf`:

```hcl title="envs/dev/main.tf"
terraform {
  required_version = ">= 1.10.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

provider "aws" {
  region = var.region

  default_tags {
    tags = {
      Project     = "quickcart"
      Environment = var.environment
      ManagedBy   = "terraform"
    }
  }
}

module "network" {
  source = "../../modules/network"

  name       = "quickcart-${var.environment}"
  cidr_block = var.vpc_cidr
  zone_count = var.zone_count
}

output "vpc_id" {
  description = "The ID of this environment's VPC"
  value       = module.network.vpc_id
}

output "zones" {
  description = "The availability zones this environment uses"
  value       = module.network.zones
}
```

| Setting | What it does | If you leave it out | When you'd change it |
|---|---|---|---|
| `required_version`, `required_providers` | Terraform 1.10 or later and AWS provider 6.x, the same in every environment | Each environment might run a different version | When you upgrade, in every folder at once |
| `provider "aws"` → `region = var.region` | The region is a **variable**, so the same file builds in any region | Terraform uses your login's default region, which may differ between people | Never; change the value in `terraform.tfvars` |
| `default_tags` → `tags` | Every resource this provider builds gets these tags, including ones inside modules. `Environment` comes from a variable | No tags unless each resource sets its own | To add tags your team requires everywhere |
| `module "network"` → `source` | The shared module, two folders up. Every environment points at the same one | Required | Never per environment |
| `name` | `quickcart-dev`, `quickcart-stg`: built from the environment's name | Required by the module | — |
| `cidr_block`, `zone_count` | Passed straight through from this folder's variables | `cidr_block` is required; `zone_count` falls back to the module's default | Never here; change the values instead |
| `output "vpc_id"`, `output "zones"` | Print what was built, so you can check it | Nothing printed after apply | — |

The variables it needs:

```hcl title="envs/dev/variables.tf"
variable "environment" {
  description = "Which environment this folder builds"
  type        = string

  validation {
    condition     = contains(["dev", "stg", "prod"], var.environment)
    error_message = "environment must be dev, stg or prod."
  }
}

variable "region" {
  description = "The AWS region to build in"
  type        = string
}

variable "vpc_cidr" {
  description = "The VPC's address range. Different for every environment"
  type        = string
}

variable "zone_count" {
  description = "How many availability zones to use"
  type        = number
}
```

| Setting | What it does | If you leave it out | When you'd change it |
|---|---|---|---|
| `environment` → validation | Only `dev`, `stg` or `prod` are accepted | A typo creates resources with a strange name | When you add an environment |
| No defaults on any variable | Every environment must set every value in its own `terraform.tfvars` | A default would quietly apply to any environment that forgot to set it, like prod getting dev's range | Never, for values that should be decided per environment |
| `description`, `type` | Explain each value and reject the wrong kind | Mistakes show up later, with vaguer errors | — |

Where this environment's state lives. The only line that differs between folders is `key`:

```hcl title="envs/dev/backend.tf" ph="111122223333"
terraform {
  backend "s3" {
    bucket       = "quickcart-tfstate-111122223333"
    key          = "dev/network/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true
  }
}
```

| Setting | What it does | If you leave it out | When you'd change it |
|---|---|---|---|
| `bucket` | The one state bucket, shared by every environment | Required | Never |
| `key` | **This environment's own state file.** `dev/network/…` for dev, `stg/network/…` for stg | Required | Once, when you create the folder. Never copy it unchanged |
| `region` | Where the **bucket** is. Stays `us-east-1` even when this environment builds somewhere else | Terraform may look for the bucket in the wrong region | Only if the bucket moves |
| `encrypt`, `use_lockfile` | Encrypt the state, and allow one command at a time. [Terraform state](/lessons/terraform-state/) explains both | No encryption setting; no locking | Never |

And the values, the part that's allowed to differ:

```hcl title="envs/dev/terraform.tfvars"
environment = "dev"
region      = "us-east-1"
vpc_cidr    = "10.10.0.0/16"
zone_count  = 2
```

| Setting | What it does | If you leave it out | When you'd change it |
|---|---|---|---|
| `terraform.tfvars` | Terraform reads a file with exactly this name automatically. No `-var-file` flag needed, so nobody can forget it | Terraform asks for each value, one by one, when you plan | — |
| `environment = "dev"` | Names everything `quickcart-dev` and tags it `Environment = dev` | Asked for at plan time | — |
| `region` | Where dev is built | Asked for at plan time | For a copy in another region |
| `vpc_cidr` | dev's address range. Every environment gets a different one, so they can be connected later without clashing | Asked for at plan time | — |
| `zone_count` | Two zones for dev, to keep it small | Asked for at plan time | — |

stg's folder has the **same** `main.tf` and `variables.tf`. Only these two files are its own:

```hcl title="envs/stg/backend.tf" ph="111122223333"
terraform {
  backend "s3" {
    bucket       = "quickcart-tfstate-111122223333"
    key          = "stg/network/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true
  }
}
```

```hcl title="envs/stg/terraform.tfvars"
environment = "stg"
region      = "us-east-1"
vpc_cidr    = "10.20.0.0/16"
zone_count  = 3
```

| Setting | Why it's different for stg |
|---|---|
| `key = "stg/network/terraform.tfstate"` | stg's own memory. Nothing stg does can touch dev's state |
| `environment = "stg"` | Names and tags everything `stg` |
| `vpc_cidr = "10.20.0.0/16"` | Its own range, so it never overlaps dev's |
| `zone_count = 3` | Closer to production, which uses three zones |

<Mistake title="copying a folder with its backend">

```output title="stg's first plan says"
  # module.network.aws_vpc.this must be replaced

Plan: 8 to add, 1 to change, 6 to destroy.
```

**Why:** `envs/stg/backend.tf` still says `key = "dev/network/terraform.tfstate"`. The stg folder is reading dev's state, so dev's VPC looks like the one it manages, and stg's values mean replacing it. In a brand-new environment, any plan that says `destroy` is a warning sign.

**The fix:** don't apply. Change the `key` to stg's own path, then run `terraform init -reconfigure`, which sets the folder up again with the new backend without copying any state across. The next plan should only add.

</Mistake>

### Workspaces, and why folders are safer

Terraform has another way to keep environments apart: **workspaces**. One folder has several states, and you switch between them:

```sh
terraform workspace new stg
```

| Part | What it means |
|---|---|
| `terraform workspace new` | create a new workspace and switch to it |
| `stg` | its name |

```output
Created and switched to workspace "stg"!

You're now on a new, empty workspace. Workspaces isolate their state,
so if you run "terraform plan" Terraform will not see any existing state
for this configuration.
```

```sh
terraform workspace show
```

| Part | What it means |
|---|---|
| `terraform workspace show` | print which workspace you're in now |

```output
stg
```

With the S3 backend, the first workspace, called `default`, uses your `key` as it is. Every other workspace's state goes under `env:/`, like `env:/stg/dev/network/terraform.tfstate`. The code can read the current name as `terraform.workspace`.

| | Workspaces | One folder per environment |
|---|---|---|
| Which one am I in? | Only `terraform workspace show` says. Easy to forget | The folder you're in: it's in your prompt |
| Values for each environment | You must pass the right `-var-file` every time | `terraform.tfvars` in the folder, read automatically |
| Environments in different AWS accounts | Awkward: one backend and one login for all | Easy: each folder has its own settings |
| Applying to the wrong environment | **Easy**: same folder, same files, invisible difference | Hard: you'd have to be in the wrong folder |
| Good for | Short-lived identical copies, like one per pull request, created and destroyed by a pipeline | Long-lived environments people work in: dev, stg, prod |

Folders cost a few copied files. Workspaces save them, and hide the one thing you most need to see.

### A second region

QuickCart opening in Europe means building in `eu-west-1` (Ireland) as well as `us-east-1`. There are two ways, for two different needs.

**The everyday way: a folder whose region is different.** The region is already a variable, so a Europe copy of dev is one more folder: the same `main.tf` and `variables.tf`, with its own key and values:

```hcl title="envs/dev-eu/terraform.tfvars"
environment = "dev"
region      = "eu-west-1"
vpc_cidr    = "10.30.0.0/16"
zone_count  = 2
```

| Setting | Why |
|---|---|
| `region = "eu-west-1"` | The only reason this folder exists |
| `environment = "dev"` | It's still dev, just in Europe |
| `vpc_cidr = "10.30.0.0/16"` | Its own range. Regions are often connected later, and overlapping ranges can't be |

Its `backend.tf` uses `key = "dev-eu/network/terraform.tfstate"`, and keeps `region = "us-east-1"`, because that's where the bucket is. You'll build it in the lab.

**When one root needs two regions at once: provider aliases.** Some things must be in a particular region. The classic case: a certificate for a CloudFront distribution must be in `us-east-1`, even when everything else is in Europe. So the root has **two** AWS provider configurations, and gives the second one a name, an **alias**.

A module that needs both says so with `configuration_aliases`:

```hcl title="modules/help-site/main.tf"
terraform {
  required_providers {
    aws = {
      source                = "hashicorp/aws"
      version               = "~> 6.0"
      configuration_aliases = [aws.us_east_1]
    }
  }
}

variable "domain_name" {
  description = "The help site's address, like help.example.com"
  type        = string
}

resource "aws_s3_bucket" "site" {
  bucket_prefix = "quickcart-help-"
}

resource "aws_acm_certificate" "site" {
  provider = aws.us_east_1

  domain_name       = var.domain_name
  validation_method = "DNS"
}

output "bucket_name" {
  description = "The bucket holding the help pages"
  value       = aws_s3_bucket.site.bucket
}

output "certificate_arn" {
  description = "The certificate, for a CloudFront distribution"
  value       = aws_acm_certificate.site.arn
}
```

| Setting | What it does | If you leave it out | When you'd change it |
|---|---|---|---|
| `configuration_aliases = [aws.us_east_1]` | Says: "as well as the normal AWS provider, I need a second one, which I call `aws.us_east_1`." The caller decides which real configuration that is | Terraform warns about an undefined provider, and the module's interface doesn't say it needs two regions | When the module needs another region |
| `version = "~> 6.0"` | The provider versions the module works with | Any version is assumed to work | When the module needs a newer feature |
| `variable "domain_name"` | The site's address, from the caller | — | — |
| `aws_s3_bucket` → `bucket_prefix` | AWS adds a unique ending to the name. S3 bucket names are unique across all of AWS, in every region | Without `bucket` or `bucket_prefix`, Terraform generates a random name | Use `bucket` for an exact name |
| No `provider` on the bucket | It uses the default AWS provider: wherever the caller builds | — | — |
| `aws_acm_certificate` → `provider = aws.us_east_1` | Build this one resource with the second provider: in `us-east-1` | It would be built in the default region, where CloudFront can't use it | — |
| `domain_name` | The name the certificate is for | Required | — |
| `validation_method = "DNS"` | Prove you own the domain with a DNS record. [DNS and HTTPS](/lessons/dns-and-https/) covers this | Required | `EMAIL` if you can't add DNS records |
| `output "bucket_name"`, `output "certificate_arn"` | Hand the results back to the caller | The caller can't use them | — |

The root makes both configurations and maps them onto the module's names:

```hcl title="envs/help-site/main.tf"
terraform {
  required_version = ">= 1.10.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

provider "aws" {
  region = "eu-west-1"
}

provider "aws" {
  alias  = "virginia"
  region = "us-east-1"
}

module "help_site" {
  source = "../../modules/help-site"

  providers = {
    aws           = aws
    aws.us_east_1 = aws.virginia
  }

  domain_name = "help.example.com"
}
```

| Setting | What it does | If you leave it out | When you'd change it |
|---|---|---|---|
| The first `provider "aws"` | The **default** configuration, with no alias: Europe | Resources with no `provider` setting have nowhere to go | — |
| `alias = "virginia"` | A second configuration, referred to as `aws.virginia` | Two `provider "aws"` blocks without an alias are an error | — |
| `region = "us-east-1"` | Where the aliased configuration builds | — | — |
| `providers` → `aws = aws` | The module's default provider is the root's default: Europe | This line alone could be left out; it's the default | — |
| `providers` → `aws.us_east_1 = aws.virginia` | Fill the module's `aws.us_east_1` slot with the root's `aws.virginia`. The names on each side can differ | Terraform stops, as below | — |
| `domain_name` | The module's input | Required | — |

<Mistake title="not passing the second provider">

```output title="Terraform stops with"
Error: Missing required provider configuration

  on main.tf line 21:
  21: module "help_site" {

The child module requires an additional configuration for provider
hashicorp/aws, with the local name "aws.us_east_1".

Refer to the module's documentation to understand the intended purpose of
this additional provider configuration, and then add an entry for
aws.us_east_1 in the "providers" meta-argument in the module block to choose
which provider configuration the module should use for that purpose.
```

**Why:** the module declared it needs `aws.us_east_1`, and the root didn't say which configuration to use.

**The fix:** add the `providers` block to the `module` block, as above. And never put a `provider` block inside a module: a module that has its own provider can't be used with `count` or `for_each`, and can't be removed cleanly.

</Mistake>

<Note title="A shortcut for a single resource">

Since AWS provider 6.0, most resources also accept their own `region` setting, like `region = "us-east-1"` on the certificate. For one resource in another region, that's simpler than an alias. Aliases are still how you give a whole module, or many resources, a second region.

</Note>

### What doesn't move to a second region

"The region is just a variable" is only true if nothing else in the code belongs to one region. These are the usual ones:

| Thing | What happens in a new region | What to do |
|---|---|---|
| **Availability zone names** | `us-east-1a` doesn't exist in eu-west-1 | Look them up with `data "aws_availability_zones"`, as the network module does |
| **AMI IDs** (server images) | Each region has its own IDs for the same image | Look them up with `data "aws_ami"` |
| **ACM certificates** | Regional: a certificate in us-east-1 can't be used by a load balancer in eu-west-1 | Issue one per region. CloudFront is the exception: always us-east-1 |
| **Services and instance types** | Not every one is offered in every region | Check before you promise a date |
| **IAM roles, Route 53, CloudFront** | Global: one of each serves every region | Create them once, in one folder, not per region |
| **S3 bucket names** | Global: the name must be unique across all of AWS | Put the region in the name, or use `bucket_prefix` |
| **The state bucket** | Stays where it is | Same bucket, same backend `region`, a new `key` |
| **Cost** | Everything is paid for twice, plus data sent between regions | Build the second region small, and grow it |

<Mistake title="a zone name typed into the code">

```output title="Apply stops half-way, with a message like"
Error: creating EC2 Subnet: InvalidParameterValue: Value (us-east-1a) for parameter availabilityZone is invalid. Subnets can currently only be created in the following availability zones: eu-west-1a, eu-west-1b, eu-west-1c.
```

The exact wording may differ.

**Why:** the code named a zone from us-east-1. The VPC was created first, then the subnet was refused, so the apply stopped with half the network built.

**The fix:** look zone names up with the `aws_availability_zones` data source, as the network module does, and run `terraform apply` again. Terraform remembers the VPC it already built and carries on from there.

</Mistake>

<Part id="doit">

<Cost kind="pennies">three small state files in your S3 bucket. VPCs, subnets, internet gateways and route tables are free, and you start no servers.</Cost>

You'll build dev and stg from the same code, prove the folders differ only in values, then build dev again in Europe by changing variables. About 30 minutes.

You need the state bucket from [Terraform state](/lessons/terraform-state/), Terraform 1.10 or later, and a working AWS login. Each region allows five VPCs by default; this lab adds two to us-east-1 and one to eu-west-1.

<Step title="Write the shared module">

These are the three files of the network module from [Modules](/lessons/terraform-modules/#idea), where every line is explained. Create each one in `modules/network/`:

```hcl title="modules/network/variables.tf"
variable "name" {
  description = "Name prefix for every resource, like quickcart-dev"
  type        = string
}

variable "cidr_block" {
  description = "The VPC's address range, like 10.10.0.0/16"
  type        = string

  validation {
    condition     = can(cidrhost(var.cidr_block, 0))
    error_message = "cidr_block must be an IPv4 range, like 10.10.0.0/16."
  }
}

variable "zone_count" {
  description = "How many availability zones to spread the public subnets across"
  type        = number
  default     = 2

  validation {
    condition     = var.zone_count >= 2 && var.zone_count <= 3
    error_message = "zone_count must be 2 or 3."
  }
}

variable "tags" {
  description = "Extra tags to put on every resource in the module"
  type        = map(string)
  default     = {}
}
```

```hcl title="modules/network/main.tf"
data "aws_availability_zones" "available" {
  state = "available"
}

locals {
  zones = slice(data.aws_availability_zones.available.names, 0, var.zone_count)
}

resource "aws_vpc" "this" {
  cidr_block           = var.cidr_block
  enable_dns_hostnames = true

  tags = merge(var.tags, { Name = var.name })
}

resource "aws_internet_gateway" "this" {
  vpc_id = aws_vpc.this.id

  tags = merge(var.tags, { Name = "${var.name}-igw" })
}

resource "aws_subnet" "public" {
  for_each = { for index, zone in local.zones : zone => index }

  vpc_id                  = aws_vpc.this.id
  availability_zone       = each.key
  cidr_block              = cidrsubnet(var.cidr_block, 8, each.value)
  map_public_ip_on_launch = true

  tags = merge(var.tags, { Name = "${var.name}-public-${each.key}" })
}

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.this.id

  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.this.id
  }

  tags = merge(var.tags, { Name = "${var.name}-public" })
}

resource "aws_route_table_association" "public" {
  for_each = aws_subnet.public

  subnet_id      = each.value.id
  route_table_id = aws_route_table.public.id
}
```

<Part id="cheat">

<Cheat>

| Thing | What to remember |
|---|---|
| One folder per environment | `envs/dev`, `envs/stg`: you can see where you are |
| `main.tf`, `variables.tf` | Identical in every folder. `diff` should print nothing |
| `backend.tf` → `key` | Different per environment. Never copy it unchanged |
| `backend.tf` → `region` | Where the state bucket is, not where you build |
| `terraform.tfvars` | Read automatically. Holds everything that differs |
| No defaults on per-environment variables | So a forgotten value is an error, not dev's value in prod |
| `terraform init -reconfigure` | Set a folder up again after changing its backend, without copying state |
| `terraform workspace show` | Which workspace you're in. Fine for short-lived copies, risky for real environments |
| `provider "aws" { alias = "virginia" … }` | A second configuration, for a second region |
| `configuration_aliases = [aws.us_east_1]` | In a module: "I need a second AWS provider" |
| `providers = { aws.us_east_1 = aws.virginia }` | In the module block: which one to use |
| `data "aws_availability_zones"`, `data "aws_ami"` | Never type in zone names or image IDs |

</Cheat>
