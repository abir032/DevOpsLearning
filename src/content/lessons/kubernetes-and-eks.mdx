<Part id="idea">

**Kubernetes** does the same job as ECS: it runs your containers, restarts them when they fail, keeps a set number running, and replaces them one by one when you release. It's open source and runs anywhere: on every major cloud, and on your own servers. **EKS** is AWS's managed Kubernetes.

The big idea is how you talk to it. You don't tell Kubernetes what to **do**. You tell it what you **want**, in a file, and it keeps making that true.

<YouKnow title="You already know this: declarative UI">

In SwiftUI, Jetpack Compose or React, you don't write "add this row, then remove that one". You describe what the screen should look like for the current state, and the framework works out the changes. Kubernetes is declarative in the same way. You write `replicas: 2`; it works out whether to create a pod, delete one, or do nothing.

</YouKnow>

### The reconcile loop

Inside Kubernetes, small programs called **controllers** each watch one kind of object. Each one runs the same loop, over and over, for ever:

| Step | What happens | Example |
|---|---|---|
| **Observe** | Look at what's really running | 1 pod with the label `app: order-service` |
| **Compare** | Compare it with the **desired state** you wrote | The file says 2. One is missing |
| **Act** | Change reality to close the gap | Create one pod |

That loop is where self-healing comes from. A pod crashes, a node disappears, someone deletes a pod by mistake: the numbers stop matching, and the controller acts. Nobody has to be awake.

### The objects, compared with ECS

| Kubernetes | What it is | Closest thing on ECS |
|---|---|---|
| **Pod** | One running copy of your app: one or more containers that share a network address | Task |
| **Deployment** | Says "run N pods of this image" and handles releases | Service |
| **ReplicaSet** | Created by a Deployment, one per version. Keeps exactly N pods of that version | — ECS does this inside the service |
| **Service** | A fixed name and address in front of pods that come and go | The target group, roughly |
| **Ingress** | A request for a load balancer, with routing rules | Load balancer and listener |
| **Node** | A server that pods run on | Hidden on Fargate |
| **Namespace** | A named folder for objects, like `default` or `kube-system` | The cluster, roughly |

A **Deployment** doesn't create pods itself. It creates a **ReplicaSet** for each version of your app, and the ReplicaSet creates the pods. During a release, the Deployment grows the new ReplicaSet and shrinks the old one. That's also how `kubectl rollout undo` is instant: the old ReplicaSet is still there, just scaled to zero.

### Probes: is it alive, and is it ready?

Kubernetes checks each container with **probes**, small requests it makes on a schedule.

| Probe | The question | If it fails |
|---|---|---|
| **Readiness probe** | Can this pod take traffic right now? | The pod is taken out of the Service. It keeps running, and gets traffic again when the probe passes |
| **Liveness probe** | Is this container stuck beyond repair? | The container is restarted |
| **Startup probe** (optional) | Has a slow app finished starting? | The other probes wait until it passes |

This is a real difference from ECS. On ECS, a task failing its load balancer health check is **replaced**. On Kubernetes, a pod failing its readiness probe is only **taken out of traffic**, and a failing liveness probe restarts the container in the same pod.

<Mistake title="a liveness probe that's too strict">

Pods restart again and again under load, and `kubectl get pods` shows the `RESTARTS` count climbing.

**Why:** a liveness probe with a very short timeout fails whenever the app is briefly busy, so Kubernetes restarts healthy containers, which makes the load worse.

**The fix:** make the liveness probe lenient: a few failures in a row, a generous timeout, and an initial delay longer than start-up. Keep the strict check in the readiness probe, which only moves traffic.

</Mistake>

### What EKS runs, and what you run

A Kubernetes cluster has two halves.

| Half | What it does | On EKS, who runs it |
|---|---|---|
| **Control plane** | The API you talk to, the controllers, the scheduler, and the database of desired state | **AWS**, across several zones. About **$0.10 an hour** per cluster on standard support, roughly $73 a month |
| **Data plane** | The nodes, where pods actually run | **You**, in one of the ways below |

Each Kubernetes version gets about 14 months of standard support on EKS. After that it moves to extended support, which costs about six times more for the control plane, until you upgrade. So an EKS cluster isn't set up once: it needs upgrading, with its nodes and add-ons, for as long as it exists. Prices change; check the EKS pricing page.

| Where pods run | What it means |
|---|---|
| **Managed node group** | EC2 instances that AWS launches and helps you patch and replace. You pay for the instances. This lesson uses one |
| **Fargate** | No nodes to see: each pod gets its own small Fargate machine. Some features, like daemon sets, don't work |
| **Auto Mode** | AWS also runs the nodes and core add-ons for you, for an extra fee on top of the instances |

Every pod gets its own IP address from your subnet, and each node size has a limit. A `t3.small` holds about **11 pods**, including Kubernetes' own system pods, however much CPU is free.

### Getting traffic in

A **Service** gives pods a stable name inside the cluster, but nothing outside can reach it. To get an AWS load balancer, you install the **AWS Load Balancer Controller** into the cluster. It watches for **Ingress** objects and builds a real Application Load Balancer for each one.

To build load balancers, the controller needs AWS permissions. You give them to **that controller alone**, not to every pod on the node, with **IAM roles for service accounts** (IRSA): a Kubernetes identity linked to an IAM role. It's the same idea as ECS's task role. EKS also has a newer way to do this, called Pod Identity; the idea is the same.

### Releasing without dropped requests

The settings from [Releases without downtime](/lessons/zero-downtime-releases/) have Kubernetes equivalents:

| ECS | Kubernetes | QuickCart uses |
|---|---|---|
| Min running tasks 100% | `maxUnavailable` | 0: never go below 2 ready pods |
| Max running tasks 200% | `maxSurge` | 1: one extra pod at a time |
| Health check | Readiness probe | `/health` |
| Circuit breaker with rollback | No automatic rollback. The rollout stops and waits | `kubectl rollout undo` |

Kubernetes needs **two extra settings** that ECS handles for you. When a pod is removed, Kubernetes takes it out of the Service and sends it SIGTERM **at the same moment**. The load balancer takes a few seconds to catch up, and without help, requests arrive at a pod that has already gone.

| Setting | What it fixes |
|---|---|
| **Pod readiness gate** | A new pod only counts as ready once the **load balancer** says it's healthy, not just its own probe. So old pods aren't removed too early |
| **`preStop` sleep of 15 seconds** | The pod keeps serving for 15 seconds after it's told to stop, while the load balancer stops sending it traffic. Then SIGTERM arrives, and gunicorn finishes and exits |

`terminationGracePeriodSeconds` is Kubernetes' stop timeout. It covers the `preStop` wait **and** the app's shutdown, so QuickCart sets it to 40: 15 for the sleep, 20 for gunicorn's graceful timeout, and 5 to spare.

### Why eksctl, not the console

You can create an EKS cluster in the console, but it takes two IAM roles you create first, a cluster form, a wait, a separate node group form, and then the terminal anyway, because `kubectl` and Helm only run there. **eksctl** is AWS's recommended command-line tool for EKS. One command builds the control plane, a managed node group, their IAM roles and the networking, and connects `kubectl` to the new cluster. It uses CloudFormation underneath, so one more command deletes all of it again. This lab uses eksctl, and still uses the console wherever it has an equivalent.

```yaml title="order-service.yaml" ph="111122223333"
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/healthcheck-path: /health
    alb.ingress.kubernetes.io/target-group-attributes: deregistration_delay.timeout_seconds=30
spec:
  ingressClassName: alb
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: order-service
                port:
                  number: 80
```

#### The Deployment

| Setting | What it does | If you leave it out | When you'd change it |
|---|---|---|---|
| `apiVersion: apps/v1`, `kind: Deployment` | Which kind of object this is | Required | Never |
| `metadata.name` | The Deployment's name, used by `kubectl` commands | Required | Never, once created |
| `replicas: 2` | The desired state: 2 pods | 1 pod | To scale by hand, or let an autoscaler set it |
| `selector.matchLabels` | Which pods belong to this Deployment: those labelled `app: order-service` | Required | Never. It can't be changed after creation |
| `strategy.rollingUpdate.maxUnavailable: 0` | During a release, never have fewer than 2 ready pods | 25% of the replicas may be missing | Higher, to release faster when spare capacity doesn't matter |
| `strategy.rollingUpdate.maxSurge: 1` | During a release, run at most 1 extra pod | 25% extra, rounded up | Higher, to release faster when you have spare node capacity |
| `template.metadata.labels` | Labels on every pod. Must match the selector | The Deployment is rejected | Add labels for version or team |
| `terminationGracePeriodSeconds: 40` | Kubernetes' stop timeout: 15 s preStop + 20 s gunicorn + 5 spare | 30 seconds: gunicorn could be killed mid-request | If your requests or shutdown take longer |
| `securityContext.runAsNonRoot: true` | Refuse to start the container as root | Nothing stops a root container | Never |
| `securityContext.runAsUser: 1001` | Run as user 1001, the `appuser` from the Dockerfile | Uses the image's `USER` | Only if the image's user changes |
| `containers[].name: app` | The container's name, used by `kubectl set image` | Required | Never |
| `image` | The image to run, from ECR, by tag | Required | Every release |
| `ports.containerPort: 8080` | The port the app listens on. Mostly documentation, like `EXPOSE` | The app still works; tools that read it can't | If the app's port changes |
| `readinessProbe` | Ask `/health` every 5 s; 2 failures in a row takes the pod out of traffic | The pod gets traffic as soon as it starts, before the app is ready | Tighter for fast apps, looser for slow ones |
| `livenessProbe` | Ask `/health` every 10 s after 15 s; 3 failures in a row restart the container | A stuck app is never restarted | Keep it lenient. See the mistake in [the idea](#idea) |
| `resources.requests` | What the scheduler reserves on a node: a tenth of a CPU and 128 MB | The pod may land on a node with no room, and be squeezed | Measure real use, then set it a little above |
| `resources.limits.memory: 256Mi` | The most memory the container may use. Above it, it's killed, shown as `OOMKilled` | It can use all of a node's memory, and starve its neighbours | When the app really needs more |
| `allowPrivilegeEscalation: false` | The process can never gain more privileges than it starts with | Allowed | Never |
| `lifecycle.preStop` `sleep 15` | Keep serving for 15 s after being told to stop, while the load balancer catches up | Requests arrive at a pod that has already gone | Match it to how long your load balancer takes to deregister |

#### The Service and the Ingress

| Setting | What it does | If you leave it out | When you'd change it |
|---|---|---|---|
| Service `selector: app: order-service` | Send traffic to pods with this label, as long as they're ready | The Service has no pods behind it | Never, while the labels stay the same |
| Service `port: 80`, `targetPort: 8080` | Inside the cluster, `order-service:80` reaches the pods on 8080 | Required | If the app's port changes |
| `ingressClassName: alb` | Hand this Ingress to the AWS Load Balancer Controller | No controller claims it, and no load balancer is built | Never, on EKS with this controller |
| `alb.ingress.kubernetes.io/scheme: internet-facing` | A public load balancer | `internal`: reachable only inside the VPC | For services only other services call |
| `alb.ingress.kubernetes.io/target-type: ip` | Register pod IPs directly, like Fargate tasks | `instance`: traffic goes via a port on each node, an extra hop | Rarely |
| `alb.ingress.kubernetes.io/healthcheck-path: /health` | The ALB's health check path | `/`, which works here, but isn't a real readiness check | If the health path changes |
| `target-group-attributes: deregistration_delay.timeout_seconds=30` | The drain, as on ECS | 300 seconds: slow releases | Longer than your slowest request |
| `rules` with `path: /` and `pathType: Prefix` | Send every path to the `order-service` Service on port 80 | Required | To route different paths to different Services |

This Ingress listens on HTTP port 80 only. For HTTPS you'd add a certificate from Certificate Manager with the `alb.ingress.kubernetes.io/certificate-arn` annotation and a listener on 443, as in [Domain names and HTTPS](/lessons/dns-and-https/).

<Mistake title="the pod refuses to start as a non-root user">

If the image's Dockerfile says `USER appuser` rather than a number, the pod never starts, and `kubectl describe pod` shows:

```output
Error: container has runAsNonRoot and image has non-numeric user (appuser), cannot verify user is non-root
```

**Why:** Kubernetes can only check a user **number** is not 0. A name could mean anything.

**The fix:** use a numeric `USER 1001` in the Dockerfile, as QuickCart's does, or set `runAsUser` in the manifest.

</Mistake>

</Step>

<Step title="Release a broken version">

```sh ph="111122223333"
kubectl set image deployment/order-service app=111122223333.dkr.ecr.us-east-1.amazonaws.com/quickcart-orders:v9-broken
```

| Part | What it means |
|---|---|
| `v9-broken` | a tag that doesn't exist |

```sh

```

| Part | What it means |
|---|---|
| `kubectl get pods` | list the pods, old and new |

<See>

The two old pods still `1/1 Running`, and one new pod with the status `ErrImagePull` or `ImagePullBackOff`, `0/1`. Because `maxUnavailable` is 0, Kubernetes won't remove an old pod until a new one is ready, so the site keeps working.

</See>

This is where ECS and Kubernetes differ. ECS's circuit breaker would roll back by itself. Kubernetes **stops and waits**. `kubectl rollout status` would wait up to the Deployment's progress deadline, 10 minutes by default, then report `exceeded its progress deadline`, and still not roll back. You undo it:

```sh
kubectl rollout undo deployment/order-service
```

| Part | What it means |
|---|---|
| `kubectl rollout undo` | go back to the previous version, the v1 ReplicaSet, which never stopped running |
| `deployment/order-service` | which Deployment |

<See>

`deployment.apps/order-service rolled back`, and within a few seconds `kubectl get pods` shows only healthy pods again.

</See>

</Step>

<Step title="Clean up" cleanup>

**Do this in order.** The load balancer was built by the controller, not by eksctl. Delete the app while the controller is still running, so it removes the load balancer too.

**1. Delete the app:**

```sh
kubectl delete -f order-service.yaml
```

| Part | What it means |
|---|---|
| `kubectl delete -f` | delete every object described in the file, including the Ingress, and so the load balancer |

```output
deployment.apps "order-service" deleted
service "order-service" deleted
ingress.networking.k8s.io "order-service" deleted
```

**2. Check the load balancer has gone.** Wait two minutes, then look in **EC2 → Load balancers**. There must be no load balancer starting with `k8s-default-`. If one is still there after five minutes, delete it by hand, and its target group in **EC2 → Target groups**.

**3. Delete the cluster.** This removes the nodes, the node group, the control plane, the service account's IAM role and the other CloudFormation stacks eksctl made:

```sh
eksctl delete cluster --name quickcart-eks --region us-east-1 --wait
```

| Part | What it means |
|---|---|
| `eksctl delete cluster` | delete the cluster and everything eksctl created for it |
| `--name quickcart-eks` | which cluster |
| `--region us-east-1` | where it is |
| `--wait` | don't return until it's completely gone |

<See>

10 to 15 minutes of output, ending in a line saying all cluster resources were deleted.

</See>

**4. Delete the policy.** **IAM → Policies**, search for `QuickCartLBControllerPolicy`, select it, **Delete**, and type its name to confirm.

**5. Remove the subnet tags** (optional, harmless to keep): **VPC → Subnets**, each of the two subnets, **Tags → Manage tags**, remove `kubernetes.io/role/elb`.

**6. The image repository**, if you've finished with containers: **Amazon ECR → Repositories**, tick `quickcart-orders`, **Delete**, type `delete`.

**7. Check nothing is left:**

| Where | Should show |
|---|---|
| **EKS → Clusters** | nothing |
| **EC2 → Instances** | no running instances from this lab; the two nodes show **Terminated** |
| **EC2 → Load balancers** | nothing starting with `k8s-` |
| **CloudFormation → Stacks** | no stacks starting with `eksctl-quickcart-eks` |
| **IAM → Identity providers** | no provider mentioning this cluster. If one is left, delete it |

<See>

All five checks pass. Nothing from this lab is still billing. Check the **Billing** page tomorrow to be sure.

</See>

</Step>

<Cheat>

| Command or idea | What it does |
|---|---|
| Desired state | You write what you want; controllers keep making it true |
| Reconcile loop | Observe, compare, act. Over and over |
| Pod / Deployment / ReplicaSet | One copy / "run N copies" / one version's set of copies |
| Service / Ingress | A stable name inside the cluster / a load balancer from outside |
| Readiness vs liveness probe | Take out of traffic / restart the container |
| `kubectl apply -f FILE` | Make the cluster match a file |
| `kubectl get pods` | List pods. `describe pod NAME` explains problems in its Events |
| `kubectl delete pod NAME` | Delete one pod. The Deployment replaces it |
| `kubectl set image deployment/NAME app=IMAGE` | Release a new image |
| `kubectl rollout status` / `undo` | Watch a release / go back one version |
| EKS control plane | About $0.10 an hour on standard support. Upgrade before extended support |
| t3.small | About 11 pods, however much CPU is free |
| Zero downtime on EKS | Readiness gate label, `preStop` sleep, `terminationGracePeriodSeconds` |
| Clean up | `kubectl delete -f` first, then `eksctl delete cluster` |

</Cheat>
