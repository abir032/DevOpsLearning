<Part id="problem">

<Story who="QuickCart, the very beginning">

Maya is a mobile developer. On a weekend, she builds QuickCart: a food-ordering app with a small backend that stores the menu and the orders.

The backend runs on her laptop. Her friends install the app, order lunch, and it works. Then a local food blogger mentions QuickCart. That evening, a thousand people try it at once.

The laptop is asleep in Maya's bag. Every order fails.

</Story>

<Case title="A very common pattern: the hug of death">

A small site gets linked from a very popular one. Within minutes, thousands of real visitors arrive at a server that was sized for dozens. The site slows down, then stops answering.

This has happened so often, for so long, that it has names. In the early 2000s people called it the **Slashdot effect**, after a news site whose links took smaller sites down. Today people call it a **hug of death**. Nobody is attacking. The visitors are welcome. There is simply nothing ready to handle them.

</Case>

Maya now needs to learn a pile of things at once: servers, networks, databases, containers, Terraform, pipelines. Each one comes with a list of tools. It is hard to know where to start, or what any of it is **for**.

This course answers that by following QuickCart, one problem at a time.

</Part>

<Part id="idea">

**DevOps** is everything that happens to code after a developer writes it: getting it to users safely, often, and keeping it running once it's there.

The name joins two words, *development* and *operations*. In many companies these used to be separate teams. Developers wrote code and handed it over. An operations team ran it. Releases were slow and painful, because the people who wrote the code never saw it fail, and the people who saw it fail couldn't change it. DevOps is the idea that one team owns both halves.

<YouKnow title="You already know this: shipping to an app store">

You already run a release process. You build the app, send it to TestFlight or an internal testing track, release it to a small percentage of users, and watch the crash reports.

DevOps is the same loop for the servers your app talks to. The difference is that there's no app store doing half the work for you. You build the testing track, the gradual release and the crash reports yourself.

</YouKnow>

### Every tool answers one problem

QuickCart grows from one laptop to millions of users. At each size, something new breaks. Each module in this course is the fix for one of those breaks.

| Module | What goes wrong for QuickCart | What it teaches |

<Steps>

<Step title="Check your version of macOS">

```sh
sw_vers
```

| Part | What it means |
|---|---|
| `sw_vers` | print the name and version of the operating system (short for *software versions*) |

```output
ProductName:		macOS
ProductVersion:		27.0
BuildVersion:		26A428
```

Your version and build will differ. The tools in this course need a recent macOS. Docker Desktop, for example, supports the current version of macOS and the two before it. If your Mac is several years behind, update it first in **System Settings → General → Software Update**.

</Step>

<Step title="Check which kind of chip your Mac has">

```sh
uname -m
```

| Part | What it means |
|---|---|
| `uname` | print information about the system |
| `-m` | only the machine's hardware type |

```output
arm64
```

`arm64` means an Apple chip (M1 or later). `x86_64` means an Intel chip. Both work for this course. It matters later: a container image built on an Apple chip is built for arm64 by default, and it won't run on an Intel server unless you build it for that. The [Dockerfile lesson](/lessons/dockerfile/) shows how.

</Step>

<Step title="Check your free disk space">

```sh
df -h /
```

| Part | What it means |
|---|---|
| `df` | show how much space is free on your disks (short for *disk free*) |
| `-h` | human-readable: show sizes like `212Gi` instead of counting blocks |
| `/` | only the main disk, the one macOS runs from |

```output
Filesystem        Size    Used   Avail Capacity iused ifree %iused  Mounted on
/dev/disk3s1s1   460Gi    11Gi   212Gi     5%    453k  2.2G    0%   /
```

Look at the **Avail** column. Your numbers will differ. The **Used** column often looks strangely small on a Mac, because macOS keeps its own files on a separate part of the disk. **Avail** is the number that matters.

<Mistake title="not enough space for Docker">

If **Avail** is under about 20 GB, Docker will run out of room part-way through the containers module. It shows up as an error when you build or pull an image, like:

```output title="Docker stops with a message like"
no space left on device
```

**Why:** container images are often hundreds of megabytes each, and Docker keeps old ones until you delete them.

**The fix:** free up space before you start, and use the clean-up steps in the container lessons to delete old images as you go.

</Mistake>

</Step>
