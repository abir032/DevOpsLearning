<Part id="problem">

<Story who="QuickCart, a database on every laptop">

To test the order service properly, Priya ran MySQL in a container on her laptop. She spent an afternoon filling it with realistic test orders. That evening, tidying up, she removed every container she had.

The next morning, the database was empty. The MySQL image was still there; the orders were not.

At the same time, Leo was trying to connect the order service to that database. The app was set to connect to `localhost:3306`, which worked when both ran directly on his laptop. As soon as the app ran in a container, it failed with **connection refused**, even though MySQL was running and healthy.

</Story>

<Case title="A very common mistake">

Running a database in a container without a volume, then removing the container, is one of the most common ways people lose data with Docker. The container starts, the database works, and nothing warns you that everything it writes will be deleted with it. It usually happens during a clean-up, a rebuild, or an upgrade to a newer image, which always means a new container.

</Case>

Both problems come from the same idea: **a container is its own small, separate machine.** It has its own disk, which is thrown away with it, and its own network, with its own `localhost`. This lesson is about reaching outside both.

</Part>

<Part id="idea">

### Where a container's files go

An image is read-only. When a container starts, Docker gives it a thin **writable layer** on top of the image. Everything the container writes lands there: logs, uploads, a database's files.

That layer belongs to that one container. **Stopping** the container keeps it. **Removing** the container deletes it. A new container from the same image starts with an empty layer again.

Most of the time that's what you want: a container you can throw away and replace. But some data must outlive the container. Docker has two ways to keep it:

| Kind | What it is | Survives `docker rm`? | Good for |
|---|---|---|---|
| Writable layer | The container's own scratch space | **No** | Temporary files |
| **Named volume** | Storage Docker creates and manages, with a name you give it | **Yes** | A database's files, anything that must survive |
| **Bind mount** | A folder on your computer, shown inside the container | Yes; it's your folder | Code you're editing, config files, local development |

A volume or bind mount is attached at a folder inside the container, called its **mount point**. MySQL always writes to `/var/lib/mysql`. Mount a volume there, and MySQL's files go into the volume without MySQL knowing anything changed.

<YouKnow title="You already know this: the Photos library">

Delete an app from your phone and its sandbox goes with it: settings, caches, drafts. But the photos it saved into the shared Photos library stay, and the next app, or the same app reinstalled, can still see them.

A container's writable layer is the sandbox. A volume is the shared library: it sits outside the container, and a new container can pick it up again.

</YouKnow>

<Key>Anything a container writes outside a volume is deleted with the container.</Key>

### Two ways to write it

`docker run` accepts volumes and bind mounts in two styles. They do the same thing:

| You write | Means |
|---|---|
| `-v db-data:/var/lib/mysql` | Mount the named volume `db-data` at `/var/lib/mysql`. Docker creates it if it doesn't exist |
| `--mount type=volume,source=db-data,target=/var/lib/mysql` | The same, spelled out |
| `--mount type=bind,source=/home/maya/order-service,target=/code` | Show that folder on your computer inside the container, at `/code` |

`--mount` is longer but harder to get wrong. With `-v`, if the left side doesn't look like a path, Docker quietly treats it as a volume name. With `--mount type=bind`, a path that doesn't exist is an error, which is what you want.

### Every container has its own network

Each container gets its own network card, its own IP address, and **its own `localhost`**. Inside a container, `localhost` means that container, and nothing else.

| From | To | How |
|---|---|---|
| Your computer | A container | **Publish a port**: `-p 8080:8080` connects port 8080 on your computer to port 8080 in the container |
| A container | Another container | Put both on the **same network you created**, and use the other's **name** |
| A container | The internet | Works by default. Docker shares your computer's connection |

### Publishing ports

`-p` takes the host's port first, then the container's:

| You write | Means |
|---|---|
| `-p 8080:8080` | Port 8080 on your computer, on every network it's connected to, leads to port 8080 in the container |
| `-p 8081:8080` | Port **8081** on your computer leads to port 8080 in the container |
| `-p 127.0.0.1:8080:8080` | Only programs on your own computer can use it, not other devices on your Wi-Fi |

Containers talking to each other on the same network **don't need `-p` at all**. Publishing is only for reaching a container from outside Docker. That's why QuickCart's database will have no `-p`: only the app needs to reach it.

### Networks and names

Docker starts every container on a network called `bridge` unless you say otherwise. Containers on it can reach each other only by IP address, and addresses change every time a container is recreated.

A network **you create** is also a bridge network, with one important extra: **built-in DNS**. Every container on it can reach the others by name.

| Network | Reach others by name? | Use it for |
|---|---|---|
| The default `bridge` | No, IP only | Quick one-off containers |
| A network you create, like `quickcart` | **Yes** | Anything with more than one container |
| Separate networks | No: they can't reach each other at all | Keeping groups of containers apart |

This is the same idea as [security groups](/lessons/security-groups/): who can reach whom is decided by the network around the app, not by the app.

<Mistake title="connecting to localhost from inside a container">

The app is set to reach MySQL at `localhost:3306`. It worked on the laptop; in a container it fails with an error like:

```output title="The app logs"
pymysql.err.OperationalError: (2003, "Can't connect to MySQL server on 'localhost' ([Errno 111] Connection refused)")
```

**Why:** `localhost` is now the app's own container, and MySQL isn't running in it. The exact words depend on the library, but they all say the connection was refused.

**The fix:** put both containers on one network and connect to the database by its name, like `db:3306`. Docker Compose, below, does both for you.

</Mistake>

### Docker Compose: all of it in one file

Starting a database and an app by hand takes a network, a volume, and two long `docker run` commands, typed in the right order. **Docker Compose** describes all of that in one file, `compose.yaml`, and starts it with one command.

Compose also creates a network for the project, and each **service name becomes a hostname** on it. A service called `db` is reachable as `db`.

### In the cloud

On your computer, a volume is a folder Docker manages on your disk. In production there's no laptop, and containers move between machines, so QuickCart doesn't keep its database in a container at all. It uses a managed database, [RDS](/lessons/rds/), and files go to [S3](/lessons/s3/). Containers on ECS and Kubernetes get their own networking too, covered in [ECS on Fargate](/lessons/ecs-fargate/). What you learn here is the local version of the same ideas.

</Part>

<Cost kind="free">everything runs on your own computer.</Cost>

You'll lose a file on purpose, keep one with a volume, look into your computer from a container, connect two containers by name, and then run QuickCart's app with MySQL using Compose. About 30 minutes.

You need Docker running, and the `order-service` folder from [Writing a Dockerfile](/lessons/dockerfile/). Open a terminal in that folder.

<Steps>

<Step title="Watch a file disappear">

Start a container that writes a file and finishes:

```sh
docker run --name scratch python:3.12-slim sh -c "echo hello > /note.txt"
```

| Part | What it means |
|---|---|
| `docker run --name scratch` | start a container called `scratch`. No `--rm`, so it's kept after it finishes |
| `python:3.12-slim` | the image; you already have it from the last lesson |
| `sh -c "…"` | run the text in quotes with the container's shell |
| `echo hello > /note.txt` | inside the container: write `hello` into the file `/note.txt`. The `>` sends what `echo` prints into the file |

It prints nothing and finishes straight away. The file is in the container's writable layer. Now remove the container:

```sh
docker rm scratch
```

| Part | What it means |
|---|---|
| `docker rm scratch` | delete the container, and its writable layer with it |

```output
scratch
```

Start a new container from the same image and look for the file:

```sh
docker run --rm python:3.12-slim cat /note.txt
```

| Part | What it means |
|---|---|
| `--rm` | delete this container as soon as it finishes |
| `cat /note.txt` | print the file |

```output
cat: /note.txt: No such file or directory
```

The file went with the container. The image never had it.

</Step>

<Step title="Keep it with a named volume">

```sh
docker volume create notes
```

| Part | What it means |
|---|---|
| `docker volume create` | make a volume |
| `notes` | its name |

```output

```

Write the file into the volume this time:

```sh
docker run --rm -v notes:/data python:3.12-slim sh -c "echo hello > /data/note.txt"
```

| Part | What it means |
|---|---|
| `-v notes:/data` | mount the volume `notes` at `/data` inside the container |
| `echo hello > /data/note.txt` | write the file inside `/data`, which is the volume |

```sh

| Part | What it means |
|---|---|
| `-v notes:/data` | a brand-new container, given the same volume |
| `cat /data/note.txt` | print the file from the volume |

```

<Step title="Look into your computer with a bind mount">

A bind mount needs the **full path** of a folder. Ask the terminal where you are:

```sh
pwd
```

| Part | What it means |
|---|---|
| `pwd` | print working directory: the full path of the folder you're in |

```output title="Something like"
/home/maya/order-service
```

Copy what yours prints, and use it in place of `FULL_PATH`:

```sh ph="FULL_PATH"
docker run --rm --mount type=bind,source=FULL_PATH,target=/code,readonly python:3.12-slim ls /code
```

| Part | What it means |
|---|---|
| `--mount type=bind` | show a folder from your computer inside the container |
| `source=FULL_PATH` | which folder: the path `pwd` printed |
| `target=/code` | where it appears inside the container |
| `readonly` | the container can read the folder but not change it |
| `ls /code` | list what's there |

<See>

Your folder's files: `Dockerfile`, `app.py`, `requirements.txt`, and any other files from the last lesson. The container is looking straight at your computer's folder. Nothing was copied.

</See>

<Mistake title="a typo in the path">

With `--mount`, a folder that doesn't exist is an error rather than a surprise:

```output title="Docker stops with"
docker: Error response from daemon: invalid mount config for type "bind": bind source path does not exist: /home/maya/order-servce
```

**Why:** the path has a typo, so there's no such folder on your computer.

**The fix:** run `pwd` again and copy its output exactly. If the path contains a space, put double quotes around the whole `type=bind,…` value, or the terminal splits it in two.

</Mistake>

<Step title="Describe the app and MySQL in compose.yaml">

In the `order-service` folder, create `compose.yaml`:

```yaml title="compose.yaml"
services:
  app:
    build: .
    image: order-service:v1
    ports:
      - "8080:8080"
    depends_on:
      db:
        condition: service_healthy

  db:
    image: mysql:8.4
    environment:
      MYSQL_ROOT_PASSWORD: local-root-only
      MYSQL_DATABASE: quickcart
      MYSQL_USER: quickcart
      MYSQL_PASSWORD: local-dev-only
    volumes:
      - db-data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1"]
      interval: 5s
      timeout: 3s
      retries: 20
      start_period: 30s

volumes:
  db-data:
```

| Line | What it does | If you leave it out |
|---|---|---|
| `services:` | The containers in this project. Each name becomes a hostname on the project's network | Nothing to run |
| `app:` → `build: .` | Build the image from the Dockerfile in this folder | Compose would need an image that already exists |
| `image: order-service:v1` | The name to give that image | Compose makes up a name from the folder and service |
| `ports: "8080:8080"` | Publish port 8080 on your computer to the app. Quoted, because YAML can misread some number pairs with a colon | You couldn't reach the app from your computer |
| `depends_on:` → `condition: service_healthy` | Start the app only once the database's health check passes | The app might start before MySQL is ready to accept connections |
| `db:` → `image: mysql:8.4` | MySQL 8.4, a long-term support release | Required |
| `environment:` | Settings the MySQL image reads **the first time it starts with an empty data folder**: the root password, and a database and user to create | MySQL refuses to start without a root password setting |
| `volumes: - db-data:/var/lib/mysql` | Mount the named volume `db-data` where MySQL keeps its files | The data lives in the writable layer and dies with the container |
| `healthcheck:` → `test:` | Ask MySQL "are you alive?" over the network with `mysqladmin ping`. It answers without a password | `service_healthy` would have nothing to wait for |
| `interval`, `timeout`, `retries`, `start_period` | Check every 5 seconds, wait 3 seconds for an answer, allow 20 failures in a row, and ignore failures in the first 30 seconds while MySQL sets itself up | Docker's defaults check every 30 seconds, which makes startup slow |
| `volumes: db-data:` at the end | Declare the named volume, so Compose creates it | Compose stops with an error: the service refers to an undefined volume |

<Note title="These passwords are for your laptop only">

They're written in the file so the lab works. A real password never goes in a file you commit. [Secrets](/lessons/secrets/) shows where they go on AWS.

</Note>

The database has no `ports:` line. Only the app can reach it, over the project's network, by the name `db`.

</Step>

<Mistake title="changing the password in compose.yaml later">

You change `MYSQL_PASSWORD` in `compose.yaml`, run `docker compose up -d` again, and the new password is refused:

```output title="MySQL says"
ERROR 1045 (28000): Access denied for user 'quickcart'@'localhost' (using password: YES)
```

**Why:** the MySQL image only reads those settings the first time it starts with an **empty** `/var/lib/mysql`. The volume already holds a database, with the old password inside it.

**The fix:** use the old password, or, only if you don't need the data, delete the volume with `docker compose down -v` so MySQL sets itself up again.

</Mistake>

<Cheat>

| Command or setting | What it does |
|---|---|
| Writable layer | The container's own files. Deleted by `docker rm` |
| `docker volume create NAME` | Make a named volume |
| `-v NAME:/path` | Mount a named volume inside the container |
| `--mount type=bind,source=FULL_PATH,target=/path` | Show a folder from your computer inside the container |
| `-p 8081:8080` | Port 8081 on your computer leads to 8080 in the container |
| `-p 127.0.0.1:8080:8080` | Only reachable from your own computer |
| `docker network create NAME` | A network where containers find each other by name |
| `localhost` in a container | That container itself. Use the other container's name |
| `docker compose up -d --wait` | Start everything in `compose.yaml` and wait until healthy |
| `docker compose exec SERVICE COMMAND` | Run a command inside a service |
| `docker compose down` | Remove containers and network. Keeps volumes |
| `docker compose down -v` | Also deletes the volumes and their data |

</Cheat>
