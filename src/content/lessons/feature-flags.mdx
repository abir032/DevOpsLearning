<Part id="problem">

<Story who="QuickCart, the new checkout">

The team is rebuilding checkout. It takes six weeks, so Ana works on a separate branch. By the time it's finished, the main branch has moved on so far that merging takes two days.

The new checkout ships on a Thursday, to everyone at once. By Thursday evening, customers paying with one kind of card can't finish an order. The fix needs a new build of the server, and a new version of the mobile app. The app store review takes a day and a half.

For a day and a half, some customers can't pay, and there's nothing the team can do but wait.

</Story>

<Case title="This really happened: a forgotten flag">

In August 2012, a US stock-trading firm deployed new trading software to its eight servers. The deploy missed one of them, which kept the old code. The new release reused the name of an old flag. On the seven updated servers, the flag turned on the new feature. On the eighth, it woke up code that had been unused for years.

That server sent millions of orders nobody intended. In about 45 minutes the firm lost more than 400 million dollars, and it was taken over by another company soon after. A dead feature and its flag had been left in the code long after anyone needed them.

</Case>

QuickCart needs two things: a way to ship the new checkout without switching it on, and a way to switch it off in seconds. Feature flags give both. The case above shows what happens when you forget to clean them up.

</Part>

<Part id="idea">

A **feature flag** is an `if` in your code whose answer comes from a setting instead of being written in the code:

```js title="checkout.mjs"
import { isOn } from "./flags.mjs";

export function checkoutScreen(userId) {
  if (isOn("newCheckout", userId)) {
    return "new checkout";
  }
  return "old checkout";
}
```

Both checkouts are deployed. The setting decides, for each customer, which one runs, and you can change the setting without deploying anything.

<YouKnow title="You already know this: feature flags">

If you've used Firebase Remote Config, or any tool that changes an app's behaviour without a store release, you've used feature flags. They're exactly the same thing on a server, and just as useful there.

</YouKnow>

### Deploy is not release

The [lifecycle lesson](/lessons/devops-lifecycle/) split **deploy**, putting code on servers, from **release**, letting users have it. Flags are what make that split real:

| Without a flag | With a flag |
|---|---|
| The feature is live the moment the code is deployed | The code is deployed switched off. Nobody sees it |
| Unfinished work waits on a long branch, and merging hurts | Unfinished work is merged every day, switched off |
| Turning it off means a new deploy, or a new app version | Turning it off is changing a setting. It takes seconds |
| Everyone gets it at once | You choose who gets it, and how many |

<Key>A flag separates deploying code from releasing a feature. The code ships switched off, and a setting, not a deploy, decides who sees it.</Key>

### What flags are used for

| Kind | What it does | QuickCart example |
|---|---|---|
| **Release flag** | Hides unfinished or new work until it's ready | The new checkout, merged daily for six weeks |
| **Percentage rollout** | Gives a feature to a growing share of customers | 10%, then 50%, then everyone, watching errors each time |
| **Kill switch** | Turns something off instantly when it misbehaves | Switching the new checkout off at 3am |
| **Targeting** | Gives a feature to chosen people | The QuickCart team first, before any customer |

A percentage rollout is a [canary release](/lessons/release-strategies/) done with a flag instead of with servers.

### How a percentage stays fair

To put 10% of customers in, the code turns each customer's ID into a number from 0 to 99, called a **bucket**, using a hash: a calculation that always gives the same answer for the same input. Customers with a bucket under 10 get the feature.

The same customer always gets the same bucket. So they see the same checkout every time they open the app, and raising the rollout from 10% to 50% only adds people. Nobody has the feature taken away.

### Where the setting lives

| Where | Changing it needs | Good for |
|---|---|---|
| A value written in the code | A deploy | Nothing. That's not really a flag |
| A file the app reads while it runs | Editing the file on every server | Learning how flags work, as in the lab |
| A flag service, such as AWS AppConfig or a similar product | A click or an API call. Every server picks it up within seconds | Real use |

Whatever holds the setting, the code must decide what happens when it **can't read it**. The answer is always **off**: the old, tested behaviour.

### Flag debt

Every flag doubles the number of ways the code can behave. Two flags make four combinations; ten make over a thousand. Once a feature has fully shipped, or been dropped, its flag is just a hidden branch that nobody tests.

| Rule | Why |
|---|---|
| Every flag has an owner and a removal date | Someone is responsible for cleaning it up |
| Remove the flag, and the losing code path, soon after full rollout | Fewer hidden branches, less to test |
| Never reuse an old flag's name | A reused name can switch on code nobody meant to run: the case above |

</Part>

<Step title="Write the flag settings">

In your editor, create `flags.json` in that folder:

```json title="flags.json"
{
  "newCheckout": {
    "enabled": true,
    "percent": 10
  }
}
```

| Setting | What it does |
|---|---|
| `newCheckout` | the flag's name. The code asks for it by this name |
| `enabled` | the kill switch. `false` turns the feature off for everyone, whatever the percentage |
| `percent` | how many customers, out of 100, get the feature |

</Step>

<Step title="Write the flag code">

Create `flags.mjs` next to it:

```js title="flags.mjs"
import { readFileSync } from "node:fs";
import { createHash } from "node:crypto";

// Read the flag settings. If the file is missing or broken, use no flags,
// so every feature behind a flag is simply off.
function loadFlags() {
  try {
    return JSON.parse(readFileSync("flags.json", "utf8"));
  } catch (err) {
    console.error("Could not read flags.json, so every flag is off: " + err.message);
    return {};
  }
}

// Turn a user ID into a number from 0 to 99. The same user always gets
// the same number, so they stay in as the percentage grows.
export function bucket(flagName, userId) {
  const hash = createHash("sha256").update(flagName + ":" + userId).digest();
  return hash.readUInt32BE(0) % 100;
}

export function isOn(flagName, userId) {
  const flag = loadFlags()[flagName];
  if (!flag || !flag.enabled) return false;
  return bucket(flagName, userId) < flag.percent;
}
```

| Part | What it does |
|---|---|
| `loadFlags()` | reads `flags.json` every time a flag is checked, so a change to the file takes effect straight away, with no restart |
| `try` and `catch` | if the file can't be read or isn't valid JSON, log a warning and return no flags. **Everything falls back to off** |
| `createHash("sha256")` | a hash: scrambles the text into a number, the same way every time |
| `flagName + ":" + userId` | hash the flag name with the user, so each flag picks a different 10% of customers |
| `readUInt32BE(0) % 100` | take the first four bytes as a whole number, and keep the remainder after dividing by 100: a bucket from 0 to 99 |
| `if (!flag \|\| !flag.enabled) return false` | an unknown flag, or one with the kill switch on, is off |
| `bucket(flagName, userId) < flag.percent` | on for customers whose bucket is under the percentage |

</Step>

<Step title="Write a script to try it">

Create `try.mjs`. It asks the flag about 20 customers:

```js title="try.mjs"
import { bucket, isOn } from "./flags.mjs";

let count = 0;
for (let i = 1; i <= 20; i++) {
  const user = "user-" + i;
  const on = isOn("newCheckout", user);
  if (on) count++;
  const what = on ? "NEW checkout" : "old checkout";
  console.log(user.padEnd(8) + " bucket " + String(bucket("newCheckout", user)).padStart(2) + "  " + what);
}
console.log(count + " of 20 users see the new checkout");
```

| Part | What it does |
|---|---|
| `for (let i = 1; i <= 20; i++)` | repeat for customers 1 to 20 |
| `isOn("newCheckout", user)` | ask the flag whether this customer gets the new checkout |
| `padEnd` and `padStart` | add spaces so the columns line up |

</Step>

<Step title="Break the settings file on purpose">

  }
}

| Part | What it means |
|---|---|

The wording of the error may differ with your version of Node.js. The script prints the warning once for every customer, and ends with `0 of 20 users see the new checkout`.

<Mistake title="a flag check that crashes the app">

If `loadFlags` had no `try` and `catch`, the same broken file would stop the whole script:

```output title="Without the fallback, Node stops with"
SyntaxError: Expected double-quoted property name in JSON at position 63 (line 5 column 3)
```

**Why:** `JSON.parse` throws an error on invalid JSON, and nothing caught it. In a server, a typo in a settings file would take checkout down.

**The fix:** always catch the error, log it loudly, and fall back to **off**. That's what the lab's code does. Real flag services also check a setting is valid before they publish it.

</Mistake>

Remove the comma again when you're done.

</Step>

<Step title="Plan the flag's removal">

A flag is temporary. Once the new checkout is at 100% and has been fine for a week or two, you would:

| Delete | Where |
|---|---|
| The `if (isOn("newCheckout", userId))` check | Wherever the code asks for the flag |
| The old checkout code | The branch of the `if` that no longer runs |
| The `newCheckout` entry | `flags.json`, or the flag service |

Write the removal date down now, next to the flag. That's how flag debt is avoided.

</Step>
