<Part id="problem">

<Story who="QuickCart, a new laptop">

Priya joins QuickCart. On her first day she installs the tools from a list in a chat thread: one from a website, one with a script she pasted, one from Homebrew. It takes the whole day.

On her second day, she runs a command to delete a test bucket. It fails: the bucket doesn't exist. She checks, and her terminal is signed in to a different AWS account entirely, using access keys she'd pasted into her shell from an old tutorial the week before.

That time the mistake was harmless. With a different command, it wouldn't have been.

</Story>

<Case title="A very common mistake: the right command, the wrong account">

Engineers often have credentials for more than one AWS account on the same laptop: a test account, a staging account, production. A command that is safe in the test account, like deleting everything with a certain name, gets run in a terminal still signed in to production.

Nothing warns you. The CLI does exactly what you asked, in whichever account it found credentials for. This is why careful teams make signing in explicit, and check who they are before running anything destructive.

</Case>

Both of Priya's problems have simple fixes: install everything the same way, and know exactly where your AWS credentials come from.

</Part>

### How the AWS CLI knows who you are

Every AWS command has to prove who's asking. The CLI finds credentials by looking in several places, **in a fixed order**, and uses the first one it finds. It never looks further.

| Order | Where it looks | What sets it |
|---|---|---|
| 1 | The `--profile` option on the command | You, each time you type a command |
| 2 | The environment variables `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` | `export` in your terminal, or a tool you ran |
| 3 | The `AWS_PROFILE` environment variable, which names a profile | `export AWS_PROFILE=quickcart` |
| 4 | The profile called `default` in `~/.aws/credentials` or `~/.aws/config` | `aws configure`, often from years ago |

A **profile** is a named set of settings in `~/.aws/config`: which account, which role, which region. The `~` means your home folder. You'll make one profile, called `quickcart`, that signs in through IAM Identity Center. Its credentials expire after a few hours, so there's nothing long-lived on your laptop to leak.

There's a longer list in the AWS documentation, with things that only matter on servers. These four are the ones that trip people up on a laptop.

<YouKnow title="You already know this: .env files">

Most tools that read a `.env` file won't overwrite a variable that's already set in your shell. So a stale `export API_URL=http://localhost:3000` from last week quietly beats the value in the file, and you spend an hour wondering why the app talks to the wrong server.

AWS credentials behave the same way. A key left in an environment variable beats the profile you think you're using.

</YouKnow>

<Key>The AWS CLI uses the first credentials it finds, in a fixed order. When in doubt, run aws sts get-caller-identity before anything that changes things.</Key>

</Part>

<Step title="Install Homebrew">

Homebrew's website, **brew.sh**, offers two ways to install it: a one-line command, and a normal Mac installer package. Use the installer: it's a file you double-click, with nothing to paste.

1. Go to **brew.sh** and follow the link to the latest release, which is on GitHub.
2. Download the file ending in `.pkg`.
3. Double-click it and follow the installer.

Then **open a new Terminal window**, so it picks up the new tool, and check:

```sh
brew --version
```

| Part | What it means |
|---|---|
| `brew` | Homebrew's command |
| `--version` | print which version is installed |

```output
Homebrew 7.0.6
```

Yours may be newer.

<Mistake title="the terminal can't find brew">

```output title="The terminal says"
zsh: command not found: brew
```

**Why:** on a Mac with an Apple chip, Homebrew lives in `/opt/homebrew/bin`, and the terminal only looks for commands in the folders listed in a setting called `PATH`. The installer adds that folder for new terminal windows, so an old window doesn't know about it.

**The fix:** close the terminal window and open a new one. If it still fails, add the folder yourself. Create your shell's settings file if it doesn't exist:

```sh
touch ~/.zprofile
```

| Part | What it means |
|---|---|
| `touch` | create the file if it doesn't exist; leave it alone if it does |
| `~/.zprofile` | a settings file in your home folder that the terminal reads when it opens |

Open it in TextEdit:

```sh
open -e ~/.zprofile
```

| Part | What it means |
|---|---|
| `open` | open a file, as if you'd double-clicked it |
| `-e` | in TextEdit |
| `~/.zprofile` | the file you just made |

Add this line at the end, save, and open a new terminal window:

```sh title="~/.zprofile"
export PATH="/opt/homebrew/bin:$PATH"
```

| Part | What it means |
|---|---|
| `export PATH=` | set the list of folders the terminal searches for commands |
| `/opt/homebrew/bin` | Homebrew's folder, put first |
| `:$PATH` | followed by everything that was already in the list |

</Mistake>

</Step>

<Step title="Connect the AWS CLI to your admin user">

Find your **AWS access portal URL** first: it's in **IAM Identity Center → Dashboard → Settings summary**, and ends in `awsapps.com/start`. Then:

```sh
aws configure sso
```

| Part | What it means |
|---|---|
| `aws configure` | set up how the CLI connects to AWS |
| `sso` | through IAM Identity Center, which used to be called AWS SSO |

It asks a series of questions. Answer them like this:

| It asks | Enter |
|---|---|
| SSO session name (Recommended) | `quickcart` |
| SSO start URL | Your AWS access portal URL |
| SSO region | `us-east-1` |
| SSO registration scopes | Press <kbd>Return</kbd> to accept the default |

Your browser opens. Sign in as your admin user if asked, with your MFA, and choose **Allow access**. Back in the terminal, it finds your account and role, then asks three more questions:

| It asks | Enter |
|---|---|
| Default client Region | `us-east-1` |
| CLI default output format | `json` |
| Profile name | `quickcart` |

```output title="It finishes with"
To use this profile, specify the profile name using --profile, as shown:

aws sts get-caller-identity --profile quickcart
```

The wording may differ slightly between versions. Everything you entered is saved in `~/.aws/config`. It looks like this, with your own portal address in place of the highlighted value. There are no keys in it.

```ini title="~/.aws/config" ph="START_URL"
[profile quickcart]
sso_session = quickcart
sso_account_id = 111122223333
sso_role_name = AdministratorAccess
region = us-east-1
output = json

[sso-session quickcart]
sso_start_url = START_URL
sso_region = us-east-1
sso_registration_scopes = sso:account:access
```

| Setting | What it means |
|---|---|
| `[profile quickcart]` | the start of a profile named `quickcart` |
| `sso_session` | which sign-in session this profile uses |
| `sso_account_id` | your 12-digit account ID |
| `sso_role_name` | the permission set you were given |
| `region` and `output` | where commands run, and how results are printed |
| `[sso-session quickcart]` | how to sign in: your portal address and its region |

</Step>

<Step title="Check who you are">

```sh
aws sts get-caller-identity --profile quickcart
```

| Part | What it means |
|---|---|
| `aws sts` | the Security Token Service, which deals with identities |
| `get-caller-identity` | say who is making this request. It needs no permissions, so it always works when credentials are valid |
| `--profile quickcart` | use the `quickcart` profile |

```output
{
    "UserId": "AROA3EXAMPLEEXAMPLE1:maya",
    "Account": "111122223333",
    "Arn": "arn:aws:sts::111122223333:assumed-role/AWSReservedSSO_AdministratorAccess_1a2b3c4d5e6f7a8b/maya"
}
```

Your account number, ID and name will be yours. Check two things: **Account** is your account, and the **Arn** contains `AWSReservedSSO_AdministratorAccess`, which means you're signed in through Identity Center, not with keys.

</Step>

<Step title="Make quickcart the profile for this terminal">

Typing `--profile quickcart` every time is tiring. Set it once for the terminal window:

```sh
export AWS_PROFILE=quickcart
```

| Part | What it means |
|---|---|
| `export` | set a variable for this terminal window and every command started from it |
| `AWS_PROFILE=quickcart` | tell the AWS CLI, Terraform and other tools to use the `quickcart` profile |

Now ask the CLI where each of its settings comes from:

```sh
aws configure list
```

| Part | What it means |
|---|---|
| `aws configure list` | show the profile, keys and region in use, and where each one came from |

```output
      Name                    Value             Type    Location
      ----                    -----             ----    --------
   profile                quickcart              env    ['AWS_PROFILE', 'AWS_DEFAULT_PROFILE']
access_key     ****************ABCD              sso
secret_key     ****************WXYZ              sso
    region                us-east-1      config-file    ~/.aws/config
```

The layout may differ slightly. The **Type** column is the useful part: `sso` means the keys came from your Identity Center sign-in. If it says `env`, keys in environment variables are winning.

To have it in every new terminal window, add the same `export AWS_PROFILE=quickcart` line to `~/.zprofile`, the way the Homebrew mistake above shows.

<Mistake title="old keys in the environment win">

If `aws configure list` shows this:

```output
access_key     ****************QRST              env
```

**Why:** `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` are set in this terminal, maybe from a tutorial. They come before `AWS_PROFILE`, so the CLI uses them and ignores your profile.

**The fix:** remove them from this terminal:

```sh
unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN
```

| Part | What it means |
|---|---|
| `unset` | delete variables from this terminal |
| `AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN` | the three variables that can hold keys |

If they come back in every new window, look for them in `~/.zprofile` or `~/.zshrc` and delete those lines.

</Mistake>

<Mistake title="the next morning, everything fails">

```output title="Any command says"
Error when retrieving token from sso: Token has expired and refresh failed
```

**Why:** that's the safety feature working. Your sign-in lasts a limited time, then expires.

**The fix:** sign in again. Your browser opens, as before:

```sh
aws sso login --profile quickcart
```

| Part | What it means |
|---|---|
| `aws sso login` | sign in again through IAM Identity Center |
| `--profile quickcart` | for the `quickcart` profile's session |

</Mistake>

</Step>
