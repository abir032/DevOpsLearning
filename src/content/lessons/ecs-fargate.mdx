  - q: A new task stops within a minute of starting, and its log stream in CloudWatch is empty. Where do you look first?
    answer: 2
    options:
      - t: The application's logs
        why: There are none. The app never started, so it never wrote anything.
      - t: The load balancer's access logs
        why: The task never got as far as receiving traffic.
      - t: The stopped task's stopped reason
        why: When ECS can't even start a task — no image, no permission, no route to ECR — it writes why on the stopped task. That's where the answer is.
      - t: The EC2 instances list
        why: On Fargate there are no instances of yours to look at.
  - q: The order service needs to read a file from S3 while it runs. Which role gets that permission?
    answer: 1
    options:
      - t: The execution role
        why: The execution role is used by ECS before your app starts — to pull the image and send logs. Your code doesn't use it.
      - t: The task role
        why: The task role is what your code's AWS calls run as. Give it just s3:GetObject on that bucket.
      - t: The service-linked role
        why: That role lets ECS itself manage load balancer targets and network cards in your account. Never add your app's permissions to it.
      - t: Both, to be safe
        why: That gives ECS's own start-up steps permissions they never need. Least privilege means each role gets only what its job needs.
  - q: Why must the target group's target type be "IP addresses" for Fargate?
    answer: 0
    options:
      - t: Each Fargate task has its own network card and private IP, and there's no instance of yours to register
        why: With the awsvpc network mode, the task itself is the thing on the network. The service registers each task's IP with the target group.
      - t: Fargate tasks don't have ports
        why: They do — 8080 here. The target group sends traffic to that port on each task's IP.
      - t: Instance targets cost more
        why: The target type doesn't change the price. It's about what exists to register.
      - t: IP targets are faster
        why: Speed isn't the reason. On Fargate, "Instance" isn't even possible.
  - q: The service's desired count is 2. You stop one of its tasks by hand. What happens?
    answer: 3
    options:
      - t: The service now runs 1 task, until you start another
        why: That's what plain docker run would do. A service's job is to prevent exactly this.
      - t: The service's desired count changes to 1
        why: Stopping a task doesn't change what you asked for. Desired stays at 2.
      - t: The whole service restarts
        why: The other task keeps serving the whole time. Only the missing one is replaced.
      - t: The service notices running is 1 but desired is 2, and starts a replacement
        why: The service keeps comparing desired with running, and closes any gap. That's the self-healing.
  - q: QuickCart's tasks run in public subnets with a public IP, but no NAT gateway. What stops anyone on the internet reaching port 8080 on a task directly?
    answer: 1
    options:
      - t: Nothing — that's the risk of skipping the NAT gateway
        why: The security group is still there, and it decides.
      - t: The task's security group only allows port 8080 from the load balancer's security group
        why: A public IP gives the task a way out to pull its image. The security group is what decides who may come in, and it names only the load balancer.
      - t: Fargate blocks all inbound traffic by default
        why: Fargate applies whatever security group you give the task. The protection comes from your rule.
      - t: The public IP changes too often to be found
        why: Scanners find new addresses within minutes. Relying on that would be no protection at all.
  - q: In the task definition, what does cpu set to 256 mean?
    answer: 2
    options:
      - t: 256 CPUs
        why: ECS counts CPU in units where 1024 is one whole vCPU.
      - t: 256 MB of memory for the CPU
        why: Memory is a separate setting. This one is compute.
      - t: A quarter of a vCPU
        why: 1024 units is one vCPU, so 256 is a quarter. With it, Fargate allows 512, 1024 or 2048 MB of memory.
      - t: The maximum requests per second
        why: ECS has no such setting. The CPU number is only the task's share of a processor.

<Part id="problem">

<Story who="QuickCart, launch month">

QuickCart's order service runs in a container on one EC2 server. Leo started it with `docker run`, and it worked.

At 3 a.m. on a Saturday, the container ran out of memory and stopped. Nothing started it again. Orders failed until Noor checked her phone at 8.

On Monday, releasing the fix meant Leo logging in to the server, stopping the old container and starting the new one. For about a minute, there was no container at all. Customers saw errors.

</Story>

<Case title="A very common mistake">

Teams move to containers, then run them with plain `docker run` on one or two servers they look after by hand. It feels finished, because the container starts the same way every time.

But nothing is watching. A container that stops stays stopped. A server that dies takes every container on it. Every release is a person typing commands on a live server. The container solved packaging. It didn't solve running.

</Case>

QuickCart needs something that keeps a set number of copies running, spreads them across zones, replaces any that die, and connects them to the load balancer. That's a **container orchestrator**. On AWS, the simplest one is **ECS**.

</Part>

<Part id="idea">

**ECS**, Elastic Container Service, runs containers for you. You describe the container once, say how many copies you want, and ECS keeps that many running.

### What an orchestrator does

| Job | Without one | With ECS |
|---|---|---|
| Put a container somewhere to run | You pick a server and run `docker run` | ECS finds room for it |
| Keep it running | Nobody notices when it stops | A stopped copy is replaced automatically |
| Run several copies across zones | You start each one by hand | You set a number; ECS spreads them |
| Connect copies to the load balancer | You register each server | ECS registers and removes them |
| Release a new version | Stop old, start new, by hand | ECS replaces copies one batch at a time |

### The four ECS words

| Word | What it is | The EC2 version you already know |
|---|---|---|
| **Cluster** | A named group for your services. On Fargate it holds no servers | — |
| **Task definition** | The recipe: which image, how much CPU and memory, which port, where logs go | A launch template |
| **Task** | One running copy of a task definition | One EC2 instance |
| **Service** | Keeps a set number of tasks running, and connects them to a load balancer | An Auto Scaling group |

Every change to a task definition makes a new numbered **revision**, like `order-service:1`, `order-service:2`. Old revisions stay exactly as they were, so going back is just choosing an earlier number.

### Fargate: no servers of your own

ECS can run tasks in two ways:

| | Fargate | EC2 |
|---|---|---|
| Servers | None that you see. AWS runs them | EC2 instances in your account |
| Patching servers | AWS does it | You do it |
| You pay for | The CPU and memory each task asks for, while it runs | Every instance, busy or not |
| Cheapest when | Load is small, or goes up and down | Load is large and steady |

QuickCart uses **Fargate**. It costs a little more per hour of computing, but there is no server to patch, resize or replace. [Auto scaling](/lessons/auto-scaling/) showed how much work servers are.

### The task definition, every field explained

This is QuickCart's task definition as JSON. The console builds exactly this from its form, and you can also paste it in directly, which you'll do in the lab.

```json title="order-service-task.json" ph="111122223333"
{
  "family": "order-service",
  "requiresCompatibilities": ["FARGATE"],
  "networkMode": "awsvpc",
  "cpu": "256",
  "memory": "512",
  "runtimePlatform": {
    "operatingSystemFamily": "LINUX",
    "cpuArchitecture": "X86_64"
  },
  "executionRoleArn": "arn:aws:iam::111122223333:role/ecsTaskExecutionRole",
  "containerDefinitions": [
    {
      "name": "app",
      "image": "111122223333.dkr.ecr.us-east-1.amazonaws.com/quickcart-orders:v1",
      "essential": true,
      "portMappings": [
        { "containerPort": 8080, "protocol": "tcp" }
      ],
      "logConfiguration": {
        "logDriver": "awslogs",
        "options": {
          "awslogs-group": "/ecs/order-service",
          "awslogs-region": "us-east-1",
          "awslogs-stream-prefix": "ecs"
        }
      }
    }
  ]
}
```

| Field | What it does | If you leave it out | When you'd change it |
|---|---|---|---|
| `family` | The task definition's name. Each save adds a revision to this family | Required | Never; a new name is a new task definition |
| `requiresCompatibilities` | Check that this recipe can run on Fargate | ECS doesn't check Fargate's rules until you try to run it | To `EC2` if you run on your own instances |
| `networkMode` | `awsvpc`: each task gets its own network card and private IP in your subnet | Required on Fargate — it's the only mode Fargate supports | Only on the EC2 launch type |
| `cpu` | CPU for the whole task, in units where 1024 is one vCPU. `256` is a quarter | Required on Fargate | When the app needs more. Load tests tell you |
| `memory` | Memory for the whole task, in MB. Must be a size Fargate allows for that CPU | Required on Fargate | With `cpu`. Too little and the task is killed for running out of memory |
| `runtimePlatform` | Linux on Intel/AMD processors — matches `--platform linux/amd64` from the build | Defaults to Linux on X86_64 | To `ARM64` if you build ARM images. Fargate on ARM costs less |
| `executionRoleArn` | The IAM role ECS uses **before your app starts**: pull the image from ECR, send logs | ECS can't pull from a private ECR repository or send logs, so the task fails to start | Only to point at a different role |
| `taskRoleArn` (not used here) | The IAM role **your code** uses for its own AWS calls | Your code has no AWS permissions. Fine here — the order service doesn't call AWS | When the app reads S3, a secret or a queue |
| `containerDefinitions` | The containers in the task. Usually one | Required | To add a helper container, such as a log shipper |
| `name` | The container's name. The service uses it to know which container gets load balancer traffic | Required | Rarely |
| `image` | The full image URI to pull, with its tag | Required | For every release: `v1`, then `v2` |
| `essential` | If this container stops, stop the whole task | Defaults to `true` | Set `false` only for optional helper containers |
| `portMappings` | The port the app listens on inside the container, and its protocol | The load balancer has no port to send traffic to | If the app's port changes |
| `logConfiguration` → `logDriver` | `awslogs`: send everything the app prints to CloudWatch Logs | Output is thrown away. You can't see why a task crashed | Rarely |
| `awslogs-group` | The CloudWatch log group to write to. It must exist already | Required with `awslogs` | One group per service |
| `awslogs-region` | The region of that log group | Required with `awslogs` | If logs go to another region |
| `awslogs-stream-prefix` | Start of each log stream's name. Streams are named `ecs/app/TASK_ID`, so you can find one task's output | Required on Fargate | Rarely |

Fargate only accepts certain CPU and memory pairs. For the small sizes:

| `cpu` | Allowed `memory` |
|---|---|
| `256` (0.25 vCPU) | `512`, `1024`, `2048` |
| `512` (0.5 vCPU) | `1024` to `4096`, in steps of 1024 |
| `1024` (1 vCPU) | `2048` to `8192`, in steps of 1024 |

### Every task gets its own IP address

With `awsvpc`, a task is a full member of your VPC, like a small server:

- Its **security group** applies to the task itself.
- The load balancer's **target group must use IP addresses** as targets, not instances. There's no instance of yours to register.
- Each task uses one IP in its subnet. A busy service can run a small subnet out of addresses.

### Two roles, easy to mix up

| Role | Used by | When | For | If it's wrong |
|---|---|---|---|---|
| **Execution role** | ECS itself | Before your app starts | Pull the image, send logs, fetch secrets | The task **never starts**. No app logs. The **stopped reason** says why |
| **Task role** | Your code | While your app runs | Anything your code does in AWS | The task runs fine, then your app logs **AccessDenied** errors |

### The service and the load balancer

A **service** holds a **desired count** — how many tasks you want. It keeps comparing that number with what's running and closes the gap. A task stops, a zone has a problem, a release starts: it's always the same loop.

When a task starts, the service registers its IP with the target group. The load balancer only sends it traffic once it passes the health check on `/health`. When a task stops, the service removes it from the target group first.

<Key>You never start tasks yourself. You set a desired count, and the service keeps reality matching it.</Key>

</Part>

<Cheat>

| Term or setting | In one line |
|---|---|
| Cluster | A named group for services. Holds no servers on Fargate |
| Task definition | The recipe: image, CPU, memory, port, logs, roles. Every change is a new revision |
| Task | One running copy of a task definition |
| Service | Keeps the desired count of tasks running and registered with the load balancer |
| Fargate | AWS runs the servers. You pay per task, for what it asks for |
| `awsvpc` | Each task gets its own network card, private IP and security group |
| Target type | **IP addresses** for Fargate |
| `cpu` `256` / `memory` `512` | A quarter of a vCPU and 512 MB |
| Execution role | ECS's role: pull the image, send logs, before the app starts |
| Task role | Your code's role, while it runs |
| Task stops with no logs | Read the **stopped reason** |
| Targets say "Request timed out" | Security groups or port, not code |
| `exec format error` | Image built for the wrong processor. Build with `--platform linux/amd64` |

</Cheat>
