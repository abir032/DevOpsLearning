<Part id="problem">

<Story who="QuickCart, the first busy weekend">

The QuickCart app talked to its API server using the server's public IP address. One Friday the server was stopped and started to change its size. It came back with a **new IP**. Every copy of the app in the world was now calling an address that went nowhere, until a new app release went out.

The next weekend was busy. One server couldn't keep up, so Priya launched a second. But the app only knew one address, so the second server sat idle while the first one struggled.

</Story>

QuickCart needs **one address that never changes**, in front of however many servers it runs, and something that stops sending customers to a server that has broken.

<Case title="This really happens: the health check that takes everything down">

Teams add a health check, then make it "thorough": it checks the database, the cache and every other service the server depends on. Then one of those shared services has a blip. **Every** server fails its check at the same moment, and the load balancer — or the auto scaling behind it — takes out the whole fleet at once.

AWS describes this pattern in its own engineering guidance (the Amazon Builders' Library article on implementing health checks): a check that's too deep turns a small, partial problem into a complete outage.

</Case>

</Part>

<Part id="idea">

A **load balancer** is one fixed address in front of many servers. Customers only ever talk to it. It passes each request on to one of the servers behind it, and it keeps checking which of those servers are healthy.

Servers can come and go, change size and change address. The address customers use never changes.

### The pieces

AWS's load balancer for websites and APIs is the **Application Load Balancer**, or ALB. It's made of a few parts that you configure separately:

| Piece | What it is | QuickCart's |
|---|---|---|
| Load balancer | The front door. It has a DNS name and sits in a **public subnet** in each zone | `quickcart-alb`, in two zones |
| Listener | A port and protocol it listens on, and what to do with requests that arrive | HTTP on 80, HTTPS on 443 |
| Rule | A condition on a listener, like "the path starts with `/orders`", and which target group gets those requests | Everything goes to one target group, for now |
| Target group | A list of servers, **plus the health check** that decides which of them get traffic | `quickcart-web-tg` |
| Target | One server in the group | Each API server |

A request's path: **customer → listener → rule → target group → one healthy target.**

### Three kinds of load balancer

| Type | Understands | Use it for |
|---|---|---|
| **Application (ALB)** | HTTP: paths, hostnames, headers | Websites and APIs. QuickCart's choice |
| Network (NLB) | Only TCP and UDP connections, not what's in them | Very high traffic, non-HTTP protocols, fixed IP addresses |
| Gateway | Network packets, sent through a security appliance | Putting firewalls in the path. You'll rarely need it |

### Health checks: who gets traffic

Every few seconds, the load balancer sends each target a small request, like `GET /health`. If the answer is right, the check passes. If it's wrong, slow or missing, it fails.

| Setting | What it means | Default | QuickCart |
|---|---|---|---|
| Path | Which URL to ask | `/` | `/health` |
| Interval | How often to ask | 30 seconds | 10 seconds |
| Timeout | How long to wait for an answer. Must be less than the interval | 5 seconds | 5 seconds |
| Unhealthy threshold | Failures in a row before the target gets no traffic | 2 | 2 |
| Healthy threshold | Passes in a row before it gets traffic again | 5 | 2 |
| Success codes | Which HTTP status counts as a pass | `200` | `200` |

**How long before a broken server stops getting traffic?** Interval × unhealthy threshold. For QuickCart that's 10 × 2 = **about 20 seconds**. Requests that reach the broken server in that window fail. Checking every second would catch it sooner, but a single slow answer would then pull a healthy server out.

<Key>Health checks decide who gets traffic. Make them answer "is this server broken?" — not "is everything behind it working?"</Key>

### Shallow or deep?

| Check | What `/health` does | When the database fails |
|---|---|---|
| **Shallow** | Answers `200` if the app is running. Touches nothing else | Every server stays in. Pages that need the database show an error. **Degraded, not down** |
| **Deep** | Also queries the database, the cache, other services | Every server fails **at once**. They're all taken out — and with auto scaling, all replaced, and the replacements fail too. **Down** |

QuickCart tested this. They removed the security group rule that let the servers reach the database. `/health` kept answering `200`, and `/` answered `500`. The site was degraded, not down: the servers stayed in, showed a clear error, and recovered the moment the rule was put back. An alarm on the error rate told a person what was wrong. A deep check would have failed all the servers together and turned a database problem into a total outage.

So database problems are a job for **alarms**, which tell a person. Health checks are for **one broken server**, which a machine can fix by replacing it.

<Note title="What an ALB does when every target is unhealthy">

If every registered target in a group fails its checks, an ALB **fails open**: it sends requests to all of them anyway, on the basis that some answer beats none. That softens the problem, but doesn't solve it. The check has stopped telling you anything, and an auto scaling group that trusts it will still start replacing every server.

</Note>

### Taking a server out gently: deregistration delay

When a target is removed on purpose — during a release, or when auto scaling shrinks the group — some requests to it may still be in progress. The **deregistration delay** stops new requests going to the target, but waits for those in progress to finish, up to a limit.

The default is **300 seconds**. That's safe, but it makes every release wait five minutes per batch. QuickCart's API answers in well under a second, so 30 seconds is plenty. This is also called connection draining.

### Status codes that come from the load balancer

When something goes wrong, the code tells you where to look:

| Code | Means | Usually |
|---|---|---|
| **502** Bad Gateway | A target was chosen, but the connection failed or the answer was broken | The app crashed or closed the connection |
| **503** Service Unavailable | There was no target to send it to | The target group is empty |
| **504** Gateway Timeout | The target took too long to answer | A slow query, or a security group dropping the traffic |

### HTTPS, and sending HTTP to it

The ALB can do the HTTPS work itself, so the servers behind it don't have to. You add a **listener on port 443**, attach a certificate from **AWS Certificate Manager** (free for use with a load balancer), and forward to the target group.

Then the listener on **port 80** changes from *forward* to **redirect**: send the browser to the same address with `https://`, with status **301**, which means "moved for good". Nobody who types the plain address gets an error, and nothing travels unencrypted. [Domain names and HTTPS](/lessons/dns-and-https/) walks through getting the certificate.

### Only the load balancer may talk to the servers

The servers shouldn't accept traffic from the internet directly. Their security group allows port 80 **only from the load balancer's security group**, not from an IP range. [Security groups](/lessons/security-groups/) explains this chain.

| Security group | Allows in |
|---|---|
| Load balancer's | 80 and 443 from anywhere |
| Servers' | 80 from the **load balancer's security group** only |

An ALB always spreads requests across targets in every zone it's in, so if one zone loses servers, the others take all the traffic. By default it takes turns, called round robin. The **least outstanding requests** setting instead sends each request to the target with the fewest in progress, which helps when some requests are much slower than others.

</Part>

<Mistake title="targets stay unhealthy with Request timed out">

```output title="Health status details"
Request timed out
```

**Why:** the health checks never reach nginx. Almost always, the servers' security group doesn't allow port 80 from the load balancer's security group — for example, the source was set to the wrong group, or to your own IP.

**The fix:** open `quickcart-app-sg` and check its inbound rule: **HTTP**, source `quickcart-alb-sg`. The next check picks up the change.

</Mistake>

<Mistake title="targets unhealthy with a 404">

```output title="Health status details"
Health checks failed with these codes: [404]
```

**Why:** the load balancer reached nginx, but there's no page at the health check path. The path is misspelled in the target group, or the user data didn't create the file.

**The fix:** check that the health check path is exactly `/health`. If it is, connect to the server with Session Manager and read `/var/log/cloud-init-output.log`.

</Mistake>

</Step>

<Mistake title="curl waits, then gives up">

```output
curl: (28) Failed to connect to ALB_DNS_NAME port 80 after 10002 ms: Timeout was reached
```

Your load balancer's name appears in place of `ALB_DNS_NAME`, and the milliseconds will differ slightly.

**Why:** the load balancer's own security group doesn't let your request in. A timeout almost always means something in the network dropped the traffic, not that the app is broken.

**The fix:** check `quickcart-alb-sg` has an inbound **HTTP** rule from `0.0.0.0/0`, and that the load balancer is using that group, not `default`.

</Mistake>

<Step title="Clean up" cleanup>

Delete things in this order. The load balancer first, because it's the most expensive, and because the security groups can't be deleted while it uses them.

<ConsolePath path="EC2 > Load balancers > quickcart-alb > Actions > Delete load balancer" />

Type `confirm` and choose **Delete**.

<ConsolePath path="EC2 > Target groups > quickcart-web-tg > Actions > Delete" />

Choose **Yes, delete**.

<ConsolePath path="EC2 > Instances > quickcart-web-a and quickcart-web-b > Instance state > Terminate instance" />

Tick both instances first. Newer consoles call it **Terminate (delete) instance**. Confirm it.

<ConsolePath path="EC2 > Security Groups > quickcart-app-sg > Actions > Delete security groups" />

Delete `quickcart-app-sg` first, then `quickcart-alb-sg`: the first one refers to the second.

<Mistake title="the security group won't delete">

```output title="The console shows a message like"
resource has a dependent object
```

**Why:** something still uses the group. The load balancer's network interfaces take a few minutes to disappear after you delete it, and a terminated instance holds on to its group until it's fully **Terminated**. Or `quickcart-app-sg` still refers to `quickcart-alb-sg`.

**The fix:** wait a few minutes, delete `quickcart-app-sg` before `quickcart-alb-sg`, and try again.

</Mistake>

Keep the `quickcart-ec2-ssm` role for the next lesson; roles are free.

No load balancers, no target groups, both instances **Terminated**, and neither security group left. Nothing is billing.

</See>
