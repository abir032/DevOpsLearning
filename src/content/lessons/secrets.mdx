quiz:
  - q: Sam committed a .env file with the database password. An hour later he deletes it in a new commit. What now?
    answer: 2
    options:
      - t: Nothing — the file is gone, so the password is safe again
        why: The file is gone from the latest commit only. Every earlier commit still holds it, and so does every clone anyone made in that hour.
      - t: Add .env to .gitignore, and that fixes it
        why: .gitignore stops a file being added in future. It does nothing about a file that's already in the history.
      - t: Treat the password as leaked and change it, then move it out of the code for good
        why: Once a secret has been pushed, you can't be sure who has seen it. Changing it makes every copy useless. Removing it from the history afterwards is tidying up, not the fix.
      - t: Make the repository private
        why: That limits who can see it from now on. It doesn't tell you who already cloned it, and the password still sits in the history for everyone who has access.
  - q: The app's policy allows GetSecretValue on the secret's ARN, written so it ends with secret:quickcart/dev/db and nothing after. Reading the secret fails with AccessDenied. Why?
    answer: 0
    options:
      - t: The real ARN ends with six random characters, so the policy needs -* at the end
        why: Secrets Manager adds a dash and six random characters to every secret's ARN. An ARN without them matches nothing. Ending the policy's resource with quickcart/dev/db-* matches the real one.
      - t: GetSecretValue is the wrong action; it should be ReadSecret
        why: There is no ReadSecret action. GetSecretValue is the right one.
      - t: Secrets can only be read by the root user
        why: Any role with the right permission can read a secret. That's the whole point of giving the app a role.
      - t: The secret must be public before a role can read it
        why: Secrets are never public. A role reads them because its policy allows it.
  - q: QuickCart's database password must change automatically every 30 days. Where should it live?
    answer: 3
    options:
      - t: In the launch template's user data
        why: Anyone who can view the template can read it, and changing it means replacing every server.
      - t: In a SecureString parameter in Parameter Store
        why: Encrypted and cheap, which is good for values that rarely change. But Parameter Store can't change a secret on a schedule by itself.
      - t: In an environment file on each server
        why: Then there's a copy on every server, and each one has to be changed by hand.
      - t: In Secrets Manager, with rotation turned on
        why: Rotation on a schedule is what Secrets Manager is for. It changes the password in the database and in the secret together, and the app reads the new value next time it asks.
  - q: The API servers have no access keys at all. How do they get permission to read the secret?
    answer: 1
    options:
      - t: The password for the secret is in the user data
        why: Secrets don't have passwords of their own. Access is decided by IAM.
      - t: An IAM role attached to the instance, whose policy allows reading that one secret
        why: The instance profile hands the server short-lived credentials for its role, and they renew by themselves. Nobody ever copies a key onto the server.
      - t: They are inside the VPC, so AWS trusts them
        why: Being inside a VPC grants no AWS permissions. Every call to Secrets Manager is checked against IAM.
      - t: Secrets Manager allows every server in the same account
        why: It allows nobody by default. Every reader needs a policy that permits it.
  - q: The password was just rotated, and the app's cached copy is now wrong. What should the app do when the database rejects it?
    answer: 2
    options:
      - t: Crash, so someone notices
        why: Every server would crash at the same moment, turning a routine rotation into an outage.
      - t: Keep retrying with the cached password
        why: The old password will never work again. Retrying it only fills the logs.
      - t: Fetch the secret again, then retry the connection once
        why: The new value is already in Secrets Manager. Fetching it again on an authentication failure is what makes rotation safe for a running app.
      - t: Nothing — rotation updates the app's memory automatically
        why: Secrets Manager can't reach into your app. The app has to ask for the new value.

<Part id="problem">

<Story who="QuickCart, a Friday afternoon">

Sam needed the API to reach the database, so he put the password where the code could find it. It went into a `.env` file next to the code, and the `.env` file went into git with everything else.

The same file held an AWS access key he had made "just for testing". A week later, a contractor was given access to the repository to fix one bug. By then the password had also been pasted into a chat thread, typed into the server's start-up script, and printed once in a log while Sam was debugging.

Nobody could say how many copies of it existed any more. So when the contractor's laptop was stolen, nobody could say whether the database was safe.

</Story>

<Case title="Keys pushed to public repositories are found within minutes">

Developers and security researchers have reported this again and again: an AWS access key pushed to a public GitHub repository is found by automated scanners, often within minutes. The key is then used to launch as many servers as the account allows, usually to mine cryptocurrency, and the owner finds out from the bill.

It's common enough that GitHub now scans public repositories for known secret formats and reports AWS keys to AWS. AWS then restricts the exposed key and emails the account owner. That is a safety net, not a plan: private repositories get copied, laptops get lost, and logs get shared.

</Case>

QuickCart needs its database password in exactly one place that it can control, with the app fetching it when it needs it.

</Part>

<Part id="idea">

A **secret** is any value that lets someone in: a database password, an API key for a payment provider, a signing key. If someone else gets a copy, they can do what your app can do.

The trouble with secrets is not storing them. It's that they get **copied**. Every copy is a place it can leak from, and every copy has to change when the secret changes.

### Where secrets usually end up

| Place | Why it leaks |
|---|---|
| In the code | Every clone of the repository has it, and git history keeps it after you delete the line |
| A `.env` file committed to git | The same. Adding it to `.gitignore` later doesn't remove it from history |
| A `.env` file on each laptop, never committed | Better, but it gets passed around in chat and email to every new developer |
| Server start-up settings (user data, environment variables) | Readable by anyone allowed to view the server's settings, and kept in every old version of the launch template |
| Logs | One debug line that prints the config, and the password is in your log system for months |
| A container image | Every layer of the image keeps its files, even ones a later step deletes. [Writing a Dockerfile](/lessons/dockerfile/) shows why |
| Terraform state | Any secret Terraform handles is stored in plain text. See [Terraform state](/lessons/terraform-state/) |

<YouKnow title="You already know this: the Keychain">

You'd never keep a user's login token in `UserDefaults` or `SharedPreferences`. It goes in the iOS Keychain or the Android Keystore, and the app asks for it when it needs it. And you know that anything shipped inside the app bundle is readable by anyone who unzips it.

Servers work the same way. A secret store is the Keychain, and your git repository is the app bundle: assume everyone can read it.

</YouKnow>

<Key>Write a secret down in exactly one place. Everything else holds only its name, and permission to read it.</Key>

### The two places AWS gives you

AWS has two services that store secrets encrypted and hand them out only to callers whose IAM policy allows it.

| | Parameter Store, SecureString | Secrets Manager |
|---|---|---|
| What it is | Part of Systems Manager. A store for settings, where a SecureString parameter is encrypted with a KMS key | A store built only for secrets |
| Cost | Standard parameters have no storage charge | About $0.40 per secret a month, plus about $0.05 per 10,000 reads. Prices change; check the pricing page |
| Changes the secret on a schedule | No. You'd have to build that yourself | Yes. This is called **rotation** |
| Largest value | 4 KB (8 KB for advanced parameters) | 64 KB |
| Keeps old values | Yes, a history of versions | Yes. The current value is labelled `AWSCURRENT` and the one before it `AWSPREVIOUS` |
| Works directly with RDS | No | Yes. RDS can create and rotate its own master password in Secrets Manager |
| Best for | Settings, and secrets that rarely change | Database passwords, and anything that should change regularly |

QuickCart puts the **database password** in Secrets Manager, because it should rotate. Settings like the database's hostname go in plain parameters or ordinary environment variables. **A hostname is not a secret.** Anyone who has it still can't log in, and putting it in a secret only means one more thing to keep in step.

### Who may read it: one role, one secret

The API servers get an **IAM role**, attached to each instance through an instance profile. [Servers on EC2](/lessons/ec2/) covers how that works. The role's policy allows reading **one** secret, and nothing else:

```json title="quickcart-read-db-secret.json" ph="111122223333"
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadTheDatabaseSecret",
      "Effect": "Allow",
      "Action": "secretsmanager:GetSecretValue",
      "Resource": "arn:aws:secretsmanager:us-east-1:111122223333:secret:quickcart/dev/db-*"
    }
  ]
}
```

| Line | What it does |
|---|---|
| `"Version": "2012-10-17"` | The version of the policy language. Always this date; it isn't the day you wrote it |
| `"Sid"` | A label for this statement, for people reading it. Optional |
| `"Effect": "Allow"` | This statement grants permission. Anything not allowed somewhere is denied |
| `"Action": "secretsmanager:GetSecretValue"` | The one thing it may do: read a secret's value. Not list secrets, not change them, not delete them |
| `"Resource"` | Which secret. `111122223333` is the account, and `quickcart/dev/db` is the secret's name |
| `-*` at the end | Secrets Manager adds a dash and six random characters to every secret's ARN, like `quickcart/dev/db-AbC123`. Without `-*`, the policy matches nothing |

A server with this role can read the database password. It can't read any other secret, and it can't even list which secrets exist. If it's ever compromised, the damage stops at that one password.

### Fetching it at run time

When the app starts, it asks Secrets Manager for the value, using its role's credentials. Here is all it takes in Python:

```python title="secret.py"
import json

import boto3

client = boto3.client("secretsmanager", region_name="us-east-1")


def db_credentials():
    response = client.get_secret_value(SecretId="quickcart/dev/db")
    return json.loads(response["SecretString"])


if __name__ == "__main__":
    creds = db_credentials()
    print("Loaded credentials for user", creds["username"])
```

| Line | What it does |
|---|---|
| `boto3.client("secretsmanager", …)` | Connect to Secrets Manager in `us-east-1`. On EC2 it finds the role's credentials by itself; there is no key in the code |
| `get_secret_value(SecretId="quickcart/dev/db")` | Ask for the secret by its name. IAM checks the role's policy, and CloudTrail records the read |
| `json.loads(response["SecretString"])` | The secret is stored as JSON, like `{"username": "…", "password": "…"}`. This turns it into a dictionary |
| `print(…, creds["username"])` | Prints the user name only. **Never log the password**, even while debugging |

The code contains the secret's **name**, and that's fine. The name is useless without a role that's allowed to read it.

Two habits make this work well in a real app:

- **Keep it in memory for a while.** Don't fetch it on every request. Every read costs a little, and it's slower. Fetching once at start, or every few minutes, is plenty.
- **When the database rejects the password, fetch it again.** That's what lets rotation happen while the app is running.

### Rotation

**Rotation** means changing a secret on a schedule, say every 30 days, so that a copy that leaked months ago stops working by itself.

Secrets Manager rotates a secret by running a small function. For a database, that function sets a new password **in the database** and saves it **in the secret**, as one job. For RDS, you can skip writing any of this: tick **Manage master credentials in AWS Secrets Manager** when you create the database, and RDS creates the secret and rotates it for you. [Managed databases: RDS](/lessons/rds/) shows where that option is.

Rotation is only safe if the app follows the second habit above. Straight after a rotation, any server with the old password cached gets rejected once, fetches the new one, and carries on.

### When a secret has leaked

The order matters:

1. **Change it first.** Once a secret has been pushed or pasted anywhere, you can't know who has it. A new value makes every copy useless.
2. **Then** move it out of the code and into Secrets Manager, so it doesn't happen again.
3. **Then**, if you like, clean it out of git history. That's tidying up, not the fix: anyone who cloned before you cleaned still has it.

</Part>

<Step title="Read the secret from the server">

Wait two or three minutes after launch, so the Session Manager agent can register. Then:

<ConsolePath path="EC2 > Instances > quickcart-secrets-lab > Connect > Session Manager > Connect" />

A terminal opens in your browser. Run:

```sh
aws secretsmanager get-secret-value --secret-id quickcart/dev/db --query SecretString --output text --region us-east-1
```

| Part | What it means |
|---|---|
| `aws secretsmanager get-secret-value` | ask Secrets Manager for a secret's value. The AWS CLI comes installed on Amazon Linux |
| `--secret-id quickcart/dev/db` | which secret, by its name |
| `--query SecretString` | from the reply, keep only the secret itself, not the extra details like its ARN and dates |
| `--output text` | print it as plain text, not wrapped in more JSON |
| `--region us-east-1` | the region the secret is in |

```output
{"username":"quickcart_app","password":"practice-only-change-me"}
```

There are no access keys on this server. The CLI got short-lived credentials for `quickcart-app-role` from the instance profile, and they renew by themselves.

<Mistake title="the policy's ARN has no -* at the end">

```output title="The command fails with"
An error occurred (AccessDeniedException) when calling the GetSecretValue operation: User: arn:aws:sts::111122223333:assumed-role/quickcart-app-role/i-0abc123example is not authorized to perform: secretsmanager:GetSecretValue on resource: quickcart/dev/db because no identity-based policy allows the secretsmanager:GetSecretValue action
```

**Why:** the secret's real ARN ends in six random characters. A policy resource of `…secret:quickcart/dev/db` matches no real secret.

**The fix:** edit `quickcart-read-db-secret` in IAM so the resource ends in `quickcart/dev/db-*`, save it, and run the command again. It can take a few seconds to apply.


| Part | What it means |
|---|---|
| `aws ssm get-parameter` | read one parameter from Parameter Store |
| `--name /quickcart/dev/db-password` | which one |
| `--with-decryption` | decrypt the SecureString. Without it you get the encrypted text |
| `--query Parameter.Value` | keep only the value |
| `--output text` | as plain text |
| `--region us-east-1` | in this region |

```output
practice-only-change-me
```

**Look at what just happened.** You never gave this role permission to read that parameter. It worked because `AmazonSSMManagedInstanceCore`, the policy that lets Session Manager connect, also allows reading **every** parameter in the account. So on any server that uses Session Manager, every SecureString parameter is readable.

<Note title="Scope parameters yourself">

If you keep secrets in Parameter Store, don't rely on AWS's broad policy. Write your own that allows `ssm:GetParameter` only on `arn:aws:ssm:us-east-1:111122223333:parameter/quickcart/dev/*`, and keep secrets off servers that use the broad one. Or, as QuickCart does, keep real secrets in Secrets Manager, where the role reads only what you name.

</Note>

<Cheat>

| Rule or command | What it means |
|---|---|
| One secret, one place | Code and settings hold the secret's name, never its value |
| Secrets Manager | Passwords and anything that should rotate. About $0.40 a secret a month |
| Parameter Store SecureString | Settings and rarely changing secrets. Standard parameters cost nothing to store |
| Policy resource | `arn:aws:secretsmanager:REGION:ACCOUNT:secret:NAME-*` — the `-*` is required |
| `aws secretsmanager get-secret-value --secret-id NAME` | Read a secret. Add `--version-stage AWSPREVIOUS` for the one before |
| `aws ssm get-parameter --name NAME --with-decryption` | Read a SecureString parameter |
| `AmazonSSMManagedInstanceCore` | Lets Session Manager in, and can read every parameter in the account |
| Rotation | Changes the secret on a schedule. The app must re-fetch when the database rejects it |
| A hostname | Not a secret. Keep it in plain config |
| Leaked? | Change it first. Clean up the code and history after |

</Cheat>
