QuickCart's order service is outgrowing its servers. The team is split. Maya wants to move it to ECS, which they already know. Leo says everyone is moving to Kubernetes, so they should too. Nobody has tried both.

In this project you settle it with evidence. You run the **same container image** on ECS Fargate and on EKS, each behind its own HTTPS load balancer. You release a new version on each while a script keeps ordering, and you count exactly how many requests fail. The target is zero. Then you write a recommendation that the other side can argue with and still not beat.

## What you'll have at the end

<TwoRuntimes />

**What to notice:** the image is identical on both sides. On ECS you create the load balancer and there are no servers. On EKS a controller builds the load balancer for you, but you now own two EC2 nodes, a controller to keep up to date, and two extra settings that ECS handles on its own.

| Piece | ECS side | EKS side |
|---|---|---|
| The image | `quickcart-orders:v1` and `v2` in ECR | the same image |
| Load balancer | `quickcart-ecs-alb`, created by you, HTTPS on 443 | created by the AWS Load Balancer Controller from an Ingress |
| What keeps two copies running | an ECS **service** with 2 tasks | a Kubernetes **Deployment** with 2 pods |
| Where they run | Fargate: no servers in your account | 2 `t3.small` EC2 nodes in your account |
| Network | the default VPC, two zones | the same default VPC and zones |
| Certificate | one self-signed certificate in ACM | the same certificate |

To keep the cost down, this project uses your account's **default VPC** with public subnets and no NAT gateway. The containers get public IP addresses only so they can download their image; their security group still lets in nothing but the load balancer. [Project 1](/projects/01-network-by-hand/) built the stricter private-subnet version, and [Project 4](/projects/04-everything-as-code/) rebuilds this project that way, in code.

## Build and run the order service

The app is small on purpose, so all your attention goes on running it. You prove it works on your computer before AWS is involved, where problems are far easier to find.

<Steps>

<Step title="Create the three files">

Make a folder called `quickcart-orders` and open it in your editor. Create these three files in it.

```python title="app.py"
import os
import socket

from flask import Flask, jsonify

app = Flask(__name__)
VERSION = os.environ.get("APP_VERSION", "v1")

ORDERS = [
    {"id": 1, "item": "margherita pizza", "qty": 2},
    {"id": 2, "item": "pad thai", "qty": 1},
    {"id": 3, "item": "mango lassi", "qty": 3},
]


@app.get("/health")
def health():
    return jsonify(status="ok", version=VERSION)


@app.get("/")
def home():
    return jsonify(service="orders", version=VERSION, served_by=socket.gethostname())


@app.get("/orders")
def orders():
    return jsonify(version=VERSION, count=len(ORDERS), orders=ORDERS)
```

| Page | What it returns | Who uses it |
|---|---|---|
| `/health` | `ok` and the version | The load balancer, to decide whether a copy may get traffic |
| `/` | the version, and the name of the copy that answered | You, to see which version and which copy served you |
| `/orders` | three example orders | You, to check the app really works |

```ini title="requirements.txt"
flask==3.1.3
gunicorn==23.0.0
```

| Line | What it means |
|---|---|
| `flask==3.1.3` | the web framework, pinned to one exact version so every build is the same |
| `gunicorn==23.0.0` | the web server that runs the app in production and stops cleanly when asked |

```dockerfile title="Dockerfile"
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py .
RUN useradd --create-home --uid 1001 appuser
USER 1001
ARG APP_VERSION=v1
ENV APP_VERSION=$APP_VERSION
EXPOSE 8080
CMD ["gunicorn", "--bind", "0.0.0.0:8080", "--workers", "2", "--graceful-timeout", "20", "app:app"]
```

| Line | What it does | Why it matters in this project |
|---|---|---|
| `FROM python:3.12-slim` | start from a small Linux with Python | small images download faster, so new copies start faster |
| `WORKDIR /app` | work in a folder called `/app` | keeps the app's files in one place |
| `COPY requirements.txt .` then `RUN pip install` | install the libraries **before** copying the code | a code change reuses the cached library layer, so builds take seconds |
| `COPY app.py .` | copy the code in | the part that changes most, so it goes last |
| `RUN useradd` and `USER 1001` | create a normal user and run as it | a break-in only gets a normal user's power |
| `ARG` and `ENV APP_VERSION` | stamp a version into the image when you build it | this is how you tell v1 from v2 during a release |
| `EXPOSE 8080` | a note that the app listens on 8080 | only root may use ports below 1024 |
| `CMD [...]` in square brackets | start gunicorn **directly**, with no shell in between | gunicorn hears the stop signal, finishes its requests and exits. This is one of the three settings that make zero failures possible |
| `--graceful-timeout 20` | give requests in progress up to 20 seconds to finish on stop | shorter than the 30-second drain you set later |

</Step>

| Part | What it means |
|---|---|

<See>

A list of build steps, ending with a line that names the image `quickcart-orders:v1`.

</See>

<Mistake title="leaving out --platform on an Apple silicon Mac">

```output title="The task or pod stops, and its log says"
exec format error
```

**Why:** your computer builds for ARM processors unless told otherwise. The image runs on your computer and fails on AWS.

**The fix:** always build with `--platform linux/amd64` when the image is going to AWS, then push again under a **new** tag. The repository is immutable, so the old tag can't be reused.

</Mistake>

</Step>

ECS and EKS both download your image from ECR, AWS's private image store.

<Steps>

<Step title="Create the repository">

<ConsolePath path="ECR > Private registry > Repositories > Create repository" />

| Field | Enter |
|---|---|
| Repository name | `quickcart-orders` |

Choose **Create**.

| Setting | Why |
|---|---|

<Step title="Log Docker in to ECR">

```sh ph="111122223333"
aws ecr get-login-password --region us-east-1 | docker login --username AWS --password-stdin 111122223333.dkr.ecr.us-east-1.amazonaws.com
```

| Part | What it means |
|---|---|
| `aws ecr get-login-password` | ask AWS for a temporary registry password |

<Mistake title="port 0, or the wrong security group on the tasks">

```output title="The target group shows the tasks as unhealthy with"
Request timed out
```

**Why:** "timed out" means the health check never arrived. That's the network, not your code. It happens when the inbound rule's port is left at `0`, or when the tasks are given `quickcart-alb-sg` instead of `quickcart-app-sg`.

**The fix:** open `quickcart-app-sg`, check the inbound rule says port `8080` from `quickcart-alb-sg`, and check the ECS service's networking uses `quickcart-app-sg` only.

</Mistake>

</Step>

<Step title="Make a self-signed certificate">

A certificate encrypts traffic and proves who the site is. ACM only issues trusted certificates for domains you own. This project doesn't need a domain, so you make a certificate yourself. It encrypts exactly as well; browsers just warn that nobody trusted vouched for it.

In the `quickcart-orders` folder:

```sh
openssl req -x509 -newkey rsa:2048 -nodes -keyout key.pem -out cert.pem -days 30 -subj "/CN=orders.quickcart.test"
```

| Part | What it means |
|---|---|
| `openssl req -x509` | make a certificate that signs itself |
| `-newkey rsa:2048` | make a new 2048-bit RSA key to go with it. ACM accepts this type |
| `-nodes` | don't put a password on the key. ACM needs it without one |
| `-keyout key.pem` | save the private key as `key.pem` |
| `-out cert.pem` | save the certificate as `cert.pem` |
| `-days 30` | valid for 30 days, plenty for this project |
| `-subj "/CN=orders.quickcart.test"` | the name written inside it. Any name works for a self-signed certificate |

<See>

Two new files in the folder: `cert.pem` and `key.pem`.

</See>

<Note title="key.pem is a secret">

It's the private half of the certificate. Never commit it to git or paste it anywhere except ACM. You delete it in [Clean up](#clean-up).

</Note>

</Step>

<Step title="Import it into Certificate Manager">

Print each file so you can copy it:

```sh
cat cert.pem
```

| Part | What it means |
|---|---|
| `cat` | print a file |
| `cert.pem` | the certificate |

<See>

Text starting `-----BEGIN CERTIFICATE-----` and ending `-----END CERTIFICATE-----`. Do the same with `cat key.pem`.

</See>

<ConsolePath path="Certificate Manager > Import" />

| Field | Enter |
|---|---|
| Certificate body | all of `cert.pem`, including the `BEGIN` and `END` lines |
| Certificate private key | all of `key.pem`, including the `BEGIN` and `END` lines |
| Certificate chain | leave empty |

Choose **Import certificate**.

<See>

The certificate listed with status **Issued** and type **Imported**. Open it and copy its **ARN**, which starts `arn:aws:acm:us-east-1:111122223333:certificate/`. EKS needs it later.

</See>

<Mistake title="ACM says the private key is not valid">

```output title="The import fails with a message like"
The private key is not supported.
```

**Why:** some versions of `openssl` write the key in a format ACM's form doesn't accept.

**The fix:** rewrite the key in the older RSA format, then paste `key-rsa.pem` instead:

```sh
openssl rsa -in key.pem -out key-rsa.pem
```

| Part | What it means |
|---|---|
| `openssl rsa` | read and rewrite an RSA key |
| `-in key.pem` | the key you made |
| `-out key-rsa.pem` | save the rewritten key under a new name |

Open `key-rsa.pem`. If its first line is `-----BEGIN RSA PRIVATE KEY-----`, it's ready. If it still says `BEGIN PRIVATE KEY`, run the command again with `-traditional` added before `-in`.

</Mistake>

<Note title="If you own a domain">

Use a trusted certificate instead and the browser warning disappears. In **Certificate Manager > Request > Request a public certificate**, enter a name such as `orders.example.com`, choose **DNS validation**, and add the record it gives you (with **Create records in Route 53** if the domain is there). Once it says **Issued**, use it everywhere this project uses the imported one, and later point `orders.example.com` at each load balancer with an alias record. [Domain names and HTTPS](/lessons/dns-and-https/) walks through it.

</Note>

</Step>

</Steps>

<See>

**Checkpoint:** two tagged subnets, two security groups in a chain (`quickcart-alb-sg` lets anyone in on 443 and 80; `quickcart-app-sg` lets only the load balancer in on 8080), and one certificate showing **Issued**.

</See>

## Release v2 on ECS under load

This is the heart of the project: release a new version while traffic flows, and count exactly how many requests failed.

<Steps>

<Step title="Create the load-testing script">

In the `quickcart-orders` folder, create `load.sh`:

```sh title="load.sh"
#!/usr/bin/env bash
# Ask one address for a page, about five times a second, and count the failures.
# Usage: bash load.sh URL SECONDS
url="$1"
seconds="${2:-180}"
if [ -z "$url" ]; then
  echo "usage: bash load.sh URL SECONDS"
  exit 1
fi
ok=0
failed=0
end=$((SECONDS + seconds))
while [ "$SECONDS" -lt "$end" ]; do
  code=$(curl --silent --insecure --output /dev/null --write-out "%{http_code}" --max-time 3 "$url")
  if [ "$code" = "200" ]; then
    ok=$((ok + 1))
  else
    failed=$((failed + 1))
    echo "$(date -u +%H:%M:%S) failed with $code"
  fi
  sleep 0.1
done
echo "----"
echo "requests: $((ok + failed))   ok: $ok   failed: $failed"
```

| Line | What it does |
|---|---|
| `url="$1"` and `seconds="${2:-180}"` | the first thing you type after the script's name is the address; the second is how many seconds to run, 180 if you leave it out |
| `if [ -z "$url" ]` | stop with a usage message if you forgot the address |
| `end=$((SECONDS + seconds))` | `SECONDS` is bash's own stopwatch. This works out when to stop |
| `while [ "$SECONDS" -lt "$end" ]` | keep going until that time |
| `code=$(curl ...)` | fetch the page and keep only the status code, like `200` or `502` |
| `--silent --insecure --output /dev/null` | print nothing, accept the self-signed certificate, and throw the page away |
| `--write-out "%{http_code}"` | print just the status code, which `$(...)` captures |
| `--max-time 3` | count anything slower than 3 seconds as a failure. A connection that never answers shows as `000` |
| `if [ "$code" = "200" ]` | 200 is success; everything else is a failure, printed with the time it happened |
| `sleep 0.1` | wait a tenth of a second between requests |
| the last two `echo` lines | print the totals: your evidence |

## Prove it

You now have numbers. Put them in one table, then write the recommendation.

| What you measured | ECS on Fargate | EKS |
|---|---|---|
| Time to create the cluster | about 1 second | your time, usually 10 to 15 minutes |
| Steps to connect a load balancer | one dropdown in the service form | a policy, a role, a Pod Identity association, a Helm install and an Ingress |
| Release under load: requests, failed | your numbers. Target: 0 failed | your numbers. Target: 0 failed |
| Undoing a broken release | automatic, a few minutes | one command, seconds, but someone has to run it |
| Settings you added for zero downtime | Min 100%, 30-second drain, `CMD` in brackets | those three, plus the readiness gate and the `preStop` wait |
| Cost before any app runs | $0 | about $73 a month, plus the nodes |
| Servers you look after | none | two nodes, and a Kubernetes upgrade every few months |

**Zero is the pass mark.** If either release showed failures, read the failure lines in window 1: the times tell you which part of the release they happened in. The [Troubleshooting](#troubleshooting) section covers the usual causes.

<Note title="Want to see why the extra EKS settings matter?">

Remove the `preStop` block from `orders.yaml`, run `kubectl apply -f orders.yaml`, and release v2 again under load. You will often see a handful of failures around the moment old pods stop. The race is timing-dependent, so if you see zero, try once more. Put the block back afterwards.

</Note>

### The recommendation

QuickCart asked a question: should new services go on ECS or EKS? Answer it in writing, with your numbers. Use this shape. It works because it ends with **what would change your mind**, which shows the answer comes from facts rather than taste.

```text title="recommendation.md"
Recommendation: ECS or EKS for new QuickCart services.

Why, in one sentence: the single deciding reason.

What we measured:
  Release under load on ECS: N requests, N failed.
  Release under load on EKS: N requests, N failed.
  Cluster creation: ECS about 1 second; EKS N minutes.
  Undoing a bad release: ECS automatic in N minutes; EKS one command in N seconds.

Operational burden: what each platform makes the team look after.
Cost at QuickCart's size: fixed monthly cost, and how it compares to the rest of the bill.
Team readiness: who knows each platform today, and how long learning the other takes.
Migration risk: what running two platforms at once would cost in releases and debugging.

The strongest argument against this, and our answer to it.

What would change our mind: for example, a real plan to run outside AWS,
a team large enough to own Kubernetes, or a tool the service needs that only one platform has.
```

Before you call it done, argue the other side. If you recommend ECS, expect "Kubernetes is the industry standard and easier to hire for" and "EKS stops us being locked in to AWS". If you recommend EKS, expect "now we run two platforms; who looks after both?" and "which Kubernetes feature does this service actually need?". Write down the strongest one and your answer. [ECS or EKS?](/lessons/ecs-or-eks/) has more on weighing them.

<Note title="Say what you didn't do">

State plainly that HTTPS used a self-signed certificate because no domain was used. The traffic is fully encrypted; with a domain, ACM would issue a trusted certificate and the browser warning would go away. Naming a limit yourself is stronger than having someone else find it.

</Note>

## Troubleshooting

Every one of these happened to someone building this project. Most are small settings, not code, which is true of real outages too. The skill is knowing where to look: the stopped reason, then the target health, then the network.

<Mistake title="every request in the load test fails with 404">

```output title="Window 1 prints"
14:02:11 failed with 404
14:02:11 failed with 404
14:02:12 failed with 404
```

**Why:** the command was typed as `bash load.sh https://ECS_ALB/10`, with no space before the `10`. The script asked for a page called `/10`, which doesn't exist, and ran for the default 180 seconds.

**The fix:** put a space between the address and the number of seconds. When numbers look wrong, check the test before blaming the system.

</Mistake>

<Mistake title="the terminal shows a > prompt and does nothing">

```output title="After pasting the loop, the terminal shows"
while>
```

**Why:** the shell is waiting for the rest of the loop. The word `done` is missing, so it thinks you're still typing.

**The fix:** press Ctrl+C and paste the whole line again, including `done`. Use the copy button so nothing gets cut off.

</Mistake>

<Mistake title="curl returns 301 instead of the page">

```output title="curl prints"
<html>
<head><title>301 Moved Permanently</title></head>
```

**Why:** the address started with `http://`, or had no scheme at all. The load balancer's port 80 listener redirects to HTTPS, which is exactly what you asked it to do.

**The fix:** use `https://` and `-k`. The redirect is working correctly.

</Mistake>

<Mistake title="ECR's scan says the image is not found">

```output title="The v1 row's artifact type shows"
Image Index
```

**Why:** without `--provenance=false`, Docker's builder (BuildKit) uploads an image index, a list, plus the real image as a separate untagged entry. ECR scans images, not lists. ECS and EKS still run it fine; they read the list and pick the right image.

**The fix:** tick the untagged entry that's about 50 MB and choose **Scan**. Next time, build with `--provenance=false`. Your message may differ slightly between console versions.

</Mistake>

<Mistake title="ECS tasks keep starting and stopping">

```output title="The service's Events tab repeats lines like"
(service orders) (port 8080) is unhealthy in (target-group arn:aws:elasticloadbalancing:us-east-1:111122223333:targetgroup/quickcart-ecs-tg/0123456789abcdef) due to (reason Request timed out).
```

**Why:** the tasks start, but the load balancer can't reach them, so ECS replaces them over and over. The two usual causes are the app security group's inbound rule (wrong port, or not from `quickcart-alb-sg`) and the tasks using the wrong security group. The circuit breaker may stop the deployment for you.

**The fix:** check **Target Groups > quickcart-ecs-tg > Targets**. "Request timed out" means the network: fix the security groups. "Health checks failed with these codes: [404]" means the path: it must be `/health`.

</Mistake>

<Mistake title="the load balancer controller stays at 0/2">

```output title="kubectl logs -n kube-system deployment/aws-load-balancer-controller shows an error about the VPC, such as"
failed to get VPC ID
```

**Why:** the `vpcId` value was empty or wrong in the `helm install` command, and the controller couldn't discover it from the node.

**The fix:** run `helm uninstall aws-load-balancer-controller -n kube-system`, then install again with the right VPC ID. If instead the log mentions `AccessDenied`, check the Pod Identity association's namespace and service account name match exactly.

</Mistake>

<Mistake title="the EKS console says you have no access to Kubernetes objects">

```output title="EKS > quickcart-eks > Resources shows"
Your current IAM principal doesn't have access to Kubernetes objects on this cluster.
```

**Why:** access to the cluster's contents is separate from access to AWS. The cluster trusts the identity that created it, and the console is logged in as someone else.

**The fix:** nothing is broken; `kubectl` still sees everything. To use the console too, add an access entry for the console identity, as in the kubectl mistake above.

</Mistake>
