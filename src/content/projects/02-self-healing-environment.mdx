On launch night, QuickCart's single server fell over at 7pm, and the app went down with it. This project builds the opposite: an environment where losing a server, or a whole zone, costs seconds of errors instead of an outage, and heals itself with nobody watching.

You'll build it by hand on top of Project 1's network, then **break it on purpose** and measure what customers would have seen: how many requests failed, and how long recovery took. "It seemed fine" doesn't count. Numbers do.

## What you'll have at the end

<Step title="Make a strong password">

The Secrets Manager console has no password generator for this kind of secret, so use the CLI in CloudShell. Open **CloudShell** from the console's top bar and run:


|---|---|

<Note title="Single-AZ or Multi-AZ: be honest about which you built">

**Multi-AZ** keeps a synchronised standby copy in the other zone. If the primary's zone fails, RDS points the same address at the standby, typically within one to two minutes, with no change to the app. It roughly doubles the database's cost.

Some account plans don't allow it. On AWS's free plan, for example, the production templates and both Multi-AZ options may be greyed out. That's a limit of the plan, not a mistake in your setup.

This guide builds **Single-AZ**, so everyone can follow it. The consequence matters later: a Single-AZ database lives in **one** zone. The zone failure test in *Prove it* then proves that the **app tier** survives losing a zone. It does **not** prove the data tier does. If your account allows Multi-AZ and you're happy to pay double for the database, choose **Multi-AZ DB instance deployment (2 instances)** here, and *Prove it* includes a failover test for you.

</Note>

<Step title="The app">

A small web app with three pages. `/` counts the orders in the database. `/health` says the server is alive, and doesn't touch the database, on purpose. `/burn` keeps the CPU busy for five seconds, to test scaling. Every request writes one line of JSON to a log file.

```python title="app.py"
"""QuickCart's orders app for Project 2."""
import json
import logging
import os
import ssl
import time
import urllib.request

import boto3
import pymysql
from flask import Flask, jsonify

REGION = os.environ["AWS_REGION"]
SECRET_ID = os.environ["SECRET_ID"]
DB_HOST = os.environ["DB_HOST"]
DB_NAME = os.environ["DB_NAME"]

METADATA = "http://169.254.169.254/latest/"


def metadata(path):
    """Ask the instance metadata service (IMDSv2) about this server."""
    token_request = urllib.request.Request(
        METADATA + "api/token",
        method="PUT",
        headers={"X-aws-ec2-metadata-token-ttl-seconds": "300"},
    )
    token = urllib.request.urlopen(token_request, timeout=2).read().decode()
    request = urllib.request.Request(
        METADATA + "meta-data/" + path,
        headers={"X-aws-ec2-metadata-token": token},
    )
    return urllib.request.urlopen(request, timeout=2).read().decode()


INSTANCE_ID = metadata("instance-id")
ZONE = metadata("placement/availability-zone")

log = logging.getLogger("quickcart")
handler = logging.FileHandler("/var/log/app/app.log")
handler.setFormatter(logging.Formatter("%(message)s"))
log.addHandler(handler)
log.setLevel(logging.INFO)


def write_log(level="INFO", **fields):
    """Write one line of JSON, so CloudWatch can filter on any field."""
    fields["level"] = level
    fields["ts"] = time.strftime("%Y-%m-%dT%H:%M:%SZ", time.gmtime())
    fields["instance_id"] = INSTANCE_ID
    fields["zone"] = ZONE
    log.info(json.dumps(fields))


secrets = boto3.client("secretsmanager", region_name=REGION)
db_login = None

TLS = ssl.create_default_context()
TLS.check_hostname = False
TLS.verify_mode = ssl.CERT_NONE


def login():
    """Read the database login from Secrets Manager once, then reuse it."""
    global db_login
    if db_login is None:
        value = secrets.get_secret_value(SecretId=SECRET_ID)["SecretString"]
        db_login = json.loads(value)
        write_log(event="secret_loaded")
    return db_login


def connect():
    """A fresh, encrypted connection per request, giving up after 3 seconds."""
    user = login()
    return pymysql.connect(
        host=DB_HOST,
        user=user["username"],
        password=user["password"],
        database=DB_NAME,
        ssl=TLS,
        connect_timeout=3,
        read_timeout=3,
    )


app = Flask(__name__)


@app.get("/health")
def health():
    return jsonify(status="ok", instance_id=INSTANCE_ID, zone=ZONE)


@app.get("/")
def orders():
    started = time.time()
    try:
        with connect() as conn:
            with conn.cursor() as cursor:
                cursor.execute("SELECT COUNT(*) FROM orders")
                (count,) = cursor.fetchone()
        took = int((time.time() - started) * 1000)
        write_log(route="/", status=200, latency_ms=took, orders=count)
        return jsonify(instance_id=INSTANCE_ID, zone=ZONE, orders=count)
    except Exception as error:
        took = int((time.time() - started) * 1000)
        write_log(
            level="ERROR",
            route="/",
            status=500,
            latency_ms=took,
            error_type=type(error).__name__,
            message=str(error)[:300],
        )
        return jsonify(error="database_unavailable", instance_id=INSTANCE_ID, zone=ZONE), 500


@app.get("/burn")
def burn():
    started = time.time()
    while time.time() - started < 5:
        pow(3, 200000)
    write_log(route="/burn", status=200, latency_ms=5000)
    return jsonify(burned=True, instance_id=INSTANCE_ID, zone=ZONE)
```

| Part | What it does |
|---|---|
| `os.environ[...]` | Reads the four settings, which the service file loads from `settings.env` |
| `metadata()` | Asks the server's metadata service for its own instance ID and zone, using the token that IMDSv2 requires. Every response and log line includes them, so you can see which server answered |
| `write_log()` | Writes each event as one line of JSON. CloudWatch can then filter on `level`, `error_type` or any other field |
| `TLS` | Encrypt the connection to the database. It doesn't check the database's certificate, because that needs AWS's RDS certificate bundle on the server. Inside a private subnet, behind the security group chain, that's an acceptable trade for a project. In production, download the bundle and verify it: [Managed databases: RDS](/lessons/rds/) shows how |
| `login()` | Reads the database login from Secrets Manager the first time it's needed, then keeps it in memory |
| `connect()` | A fresh database connection per request, which gives up after 3 seconds instead of hanging |
| `/health` | Says "ok" without touching the database. **Shallow on purpose:** see below |
| `/` | Counts the orders. If anything fails, it logs the error type and message, and returns a 500 |
| `/burn` | Five seconds of pure CPU work, to push the CPU up |

**Why `/health` doesn't check the database.** A health check that queries the database sounds more thorough. But if the database has a problem, **every** server fails its check at the same moment. The load balancer then removes all of them, and a database problem becomes a total outage, with the auto scaling group replacing perfectly healthy servers in a loop. The health check answers one question: *is this server able to serve?* Whether the database is reachable is a job for an alarm and a human.

**Why encrypt at all?** MySQL 8.4, the version RDS offers by default, signs users in with a method that needs either an encrypted connection or an extra library to send the password safely. Encrypting is the simpler and safer of the two.

</Step>

<Step title="The seeding script">

The app expects an `orders` table. This script creates the database and tables if they're missing, and adds a few sample orders. Running it twice does no harm.

```python title="seed.py"
"""Create QuickCart's database, tables and a few sample orders. Safe to run twice."""
import json
import ssl

import boto3
import pymysql

settings = {}
with open("/opt/app/settings.env") as file:
    for line in file:
        line = line.strip()
        if line and not line.startswith("#"):
            key, value = line.split("=", 1)
            settings[key] = value

secrets = boto3.client("secretsmanager", region_name=settings["AWS_REGION"])
secret = secrets.get_secret_value(SecretId=settings["SECRET_ID"])
login = json.loads(secret["SecretString"])

tls = ssl.create_default_context()
tls.check_hostname = False
tls.verify_mode = ssl.CERT_NONE

conn = pymysql.connect(
    host=settings["DB_HOST"],
    user=login["username"],
    password=login["password"],
    ssl=tls,
    connect_timeout=5,
    autocommit=True,
)

statements = [
    "CREATE DATABASE IF NOT EXISTS " + settings["DB_NAME"],
    "USE " + settings["DB_NAME"],
    """CREATE TABLE IF NOT EXISTS customers (
        id INT AUTO_INCREMENT PRIMARY KEY,
        name VARCHAR(100) NOT NULL,
        email VARCHAR(255) NOT NULL UNIQUE,
        created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
    )""",
    """CREATE TABLE IF NOT EXISTS orders (
        id INT AUTO_INCREMENT PRIMARY KEY,
        customer_id INT NOT NULL,
        amount DECIMAL(10, 2) NOT NULL,
        status ENUM('pending', 'paid', 'refunded', 'cancelled') NOT NULL DEFAULT 'pending',
        created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
        CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id) REFERENCES customers (id)
    )""",
    """INSERT IGNORE INTO customers (id, name, email) VALUES
        (1, 'Ana', 'ana@example.com'),
        (2, 'Kofi', 'kofi@example.com'),
        (3, 'Noor', 'noor@example.com')""",
    """INSERT IGNORE INTO orders (id, customer_id, amount, status) VALUES
        (1, 1, 24.50, 'paid'),
        (2, 1, 12.00, 'paid'),
        (3, 2, 31.75, 'pending'),
        (4, 2, 8.20, 'refunded'),
        (5, 3, 45.00, 'paid')""",
]

with conn:
    with conn.cursor() as cursor:
        for statement in statements:
            cursor.execute(statement)
        cursor.execute("SELECT COUNT(*) FROM orders")
        (count,) = cursor.fetchone()

print("orders in the database:", count)
```

| Part | What it does |
|---|---|
| Reading `settings.env` | Uses the same four settings as the app, so there's one place to change them |
| `get_secret_value` | Reads the login from Secrets Manager, so you never type the password |
| `CREATE DATABASE IF NOT EXISTS` | Creates the `quickcart` database if RDS didn't |
| `CREATE TABLE IF NOT EXISTS` | Two tables: customers, and their orders. Each order must belong to a real customer (`FOREIGN KEY`) |
| `INSERT IGNORE` with fixed `id`s | Adds the sample rows, and silently skips any that already exist. That's what makes running it twice safe |
| `print(…)` | Shows how many orders there are at the end |

</Step>

## Stage 5: The certificate

The load balancer won't accept an HTTPS listener without a certificate. There are two ways to get one. Choose one path and follow only that one.

| | Path A: a domain you own | Path B: self-signed |
|---|---|---|
| What you need | A domain, with its DNS in Route 53 | Nothing |
| Cost | Free certificate; the domain costs a few dollars a year | Free |
| Browsers | Trusted: a padlock, no warning | A full-page warning. Test tools must skip checking with `curl -k` |
| Renewal | Automatic, as long as the validation record stays in DNS | None: it expires after the 30 days you give it |
| Fit for real customers | Yes | **Never.** It's encrypted, but nothing proves who's on the other end |

Path B teaches everything this project is about. What it can't show you is the trust part of HTTPS, which [Domain names and HTTPS](/lessons/dns-and-https/) covers.

<Steps>

<Step title="Path A: request a public certificate">

<ConsolePath path="Certificate Manager > Request certificate" />

| Field | Enter |
|---|---|
| Certificate type | **Request a public certificate** |
| Fully qualified domain name | `shop.example.com`, using your own domain |
| Allow export | **Disable export**. Exportable certificates cost extra, and the load balancer doesn't need one |
| Validation method | **DNS validation** |
| Key algorithm | **RSA 2048** |

Choose **Request**. Open the certificate, choose **Create records in Route 53**, and then **Create records**.

<Step title="Path B: make a self-signed certificate">

In **CloudShell**:

```sh

```

| Part | What it means |
|---|---|
| `openssl req -x509` | make a certificate that signs itself, instead of a request for someone else to sign |

| `-nodes` | don't protect the key with a passphrase: the load balancer has no way to type one |
| `-days 30` | valid for 30 days |
| `-keyout quickcart.key`, `-out quickcart.crt` | the files to write: the private key and the certificate |
| `-subj "/CN=shop.example.com"` | the name the certificate is for |
| `-addext "subjectAltName=DNS:shop.example.com"` | the same name in the field that browsers and tools actually check |

It prints a few lines of dots and plus signs as it generates the key. Now print each file, to copy it:

```sh

```

| Part | What it means |
|---|---|
| `cat` | print a file's contents |
| `quickcart.crt` | the certificate |

```output

MIIDKzCCAhOgAwIBAgIUX1c3m4p8Yq2vR0bT9k6Hn5d0aWUwDQYJKoZIhvcNAQEL

```

<ConsolePath path="Certificate Manager > Import certificate" />

|---|---|

| Certificate chain | Leave empty: a self-signed certificate has no chain |

</Step>

## Stage 7: The target group

A target group isn't a network resource. It has no address. It answers two questions: which servers get traffic, and are they healthy **right now**? Every setting below is a choice you should be able to explain.

<Steps>

<Step title="Create it">

<ConsolePath path="EC2 > Target groups > Create target group" />

| Field | Enter |
|---|---|
| Choose a target type | **Instances** |
| Target group name | `quickcart-tg` |
| Protocol : Port | **HTTP** : `80` |
| IP address type | **IPv4** |
| VPC | `quickcart-vpc`. A target group can never move to another VPC, so check this one |

Open **Advanced health check settings**:

| Setting | Enter | Why |
|---|---|---|
| Health check port | **Traffic port** | Check the same port that real requests use |
| Healthy threshold | `2` | Two passes in a row before a server gets traffic |
| Unhealthy threshold | `2` | Two failures in a row before it's removed. One would react to a single blip |

## Prove it

Now break it, on purpose, and measure. The measuring runs in **CloudShell**, which is outside your VPC, like a customer.

### The measuring tools

In CloudShell, create two small scripts. Open the editor with `nano probe.sh`, paste, then save with **Ctrl+O**, **Enter**, and leave with **Ctrl+X**.

```sh title="probe.sh"
#!/bin/bash
# Usage: ./probe.sh URL RESULTS_FILE
# Every 0.2 seconds, ask URL once and add "time,status" to RESULTS_FILE.
# Stop it with Ctrl+C.
url="$1"
results="$2"
while true; do
  printf '%(%H:%M:%S)T,' -1 >> "$results"
  curl -sk -o /dev/null -w '%{http_code}\n' --max-time 3 "$url" >> "$results"
  sleep 0.2
done
```

| Line | What it does |
|---|---|
| `url="$1"`, `results="$2"` | The two things you give it: the address to test, and the file to write to |
| `while true; do` … `done` | Repeat until you press Ctrl+C |
| `printf '%(%H:%M:%S)T,' -1` | Write the current time, like `14:05:07,`. `-1` means "now" |
| `curl -sk -o /dev/null` | Make one request quietly, skip the certificate check (for path B), and throw away the page itself |
| `-w '%{http_code}\n'` | Write only the status code: `200`, `502`, and so on. A request that got no answer at all is written as `000` |
| `--max-time 3` | Give up after 3 seconds. A customer's app wouldn't wait much longer |
| `>> "$results"` | Add to the end of the file |
| `sleep 0.2` | Wait a fifth of a second, so about 4 or 5 requests a second |

Then `nano summary.sh`:

```sh title="summary.sh"
#!/bin/bash
# Usage: ./summary.sh RESULTS_FILE
# Counts the requests and the failures, and shows when the failures started and stopped.
awk -F, '
  { total++ }
  $2 != "200" { failed++; if (first == "") first = $1; last = $1 }
  END {
    printf "requests: %d\n", total
    printf "failed:   %d\n", failed
    if (failed > 0) printf "first failure: %s\nlast failure:  %s\n", first, last
  }
' "$1"
```

| Line | What it does |
|---|---|
| `awk -F,` | Read the file line by line, splitting each line at the comma: `$1` is the time, `$2` the status |
| `{ total++ }` | Count every line |
| `$2 != "200" { … }` | For any line that isn't a 200: count it as failed, and remember the first and last time that happened |
| `END { printf … }` | After the last line, print the totals |
| `"$1"` | The results file you give it |

Make both runnable:

```sh
chmod +x probe.sh summary.sh
```

| Part | What it means |
|---|---|
| `chmod +x` | mark a file as a program you can run |
| `probe.sh summary.sh` | both scripts |

It prints nothing when it works.

### How each test runs

Every test follows the same pattern:

1. Start the probe with a new results file, and leave it running for the whole test.
2. Wait about 30 seconds, so there's a clean baseline.
3. Break something, and **write down the exact time**.
4. Watch **EC2 → Target groups → quickcart-tg → Targets**, and write down when it's back to 4 healthy.
5. Stop the probe with **Ctrl+C**, and run the summary.


| `test1.csv` | where to write the results. Use a new name for each test |

With the probe running, terminate one app server directly, as if its hardware failed:

<ConsolePath path="EC2 > Instances > one quickcart-app instance > Instance state > Terminate (delete) instance" />

**What to expect.** The load balancer keeps sending that server about a quarter of the requests until two health checks fail: roughly 20 to 30 seconds. Some of those requests fail. Then the failures stop completely, and the auto scaling group launches a replacement, which is healthy again 3 to 5 minutes later.

</Step>

<Step title="Test 2: a server is removed gracefully">

With a new probe running (`test2.csv`), scale in by one, which removes a server **the planned way**:

<ConsolePath path="EC2 > Auto Scaling groups > quickcart-asg > Details > Group details > Edit" />

Set **Desired capacity** to `3` and choose **Update**. The group picks a server, **deregisters** it from the target group first, waits the 30-second deregistration delay while in-flight requests finish, and only then terminates it. When it's gone, set **Desired capacity** back to `4`.

**What to expect:** zero failed requests.

**This pair is the centre of your results.** Same outcome, a server gone, but one path respects deregistration and the other doesn't. The difference in failed requests is the difference between an outage and a routine event. It's also why releases, which replace servers on purpose, can be done with zero errors.

</Step>

<Step title="Test 3: a whole zone goes dark">

You can't switch off a real zone, but you can cut one off at the subnet, which is how AWS's own fault-injection tooling does it. A network ACL is a stateless firewall on a subnet. A **new** one denies everything until you add rules, which makes it a perfect blackhole.

<ConsolePath path="VPC > Network ACLs > Create network ACL" />

| Field | Enter |
|---|---|
| Name | `quickcart-blackhole` |
| VPC | `quickcart-vpc` |

Choose **Create network ACL**. Add no rules. Start a new probe (`test3.csv`), wait 30 seconds, and then:

<ConsolePath path="VPC > Network ACLs > quickcart-blackhole > Actions > Edit subnet associations" />

Tick `quickcart-app-a` and choose **Save changes**. Write down the time. Zone a's app servers are now cut off from everything.

**What to expect.** For about 20 to 30 seconds, requests sent to zone a's servers time out: roughly half of all requests in that window. Then the load balancer removes them, and **zone b's two servers carry everything**, with no more failures. The auto scaling group launches replacements, but any it puts in `quickcart-app-a` can't pass their health checks while the blackhole is there, so it may keep replacing them. Zone b holds the site up throughout.

Leave it for five minutes, then restore it: open the VPC's **default** network ACL, choose **Actions → Edit subnet associations**, tick `quickcart-app-a` and save. That moves the subnet back. Then delete `quickcart-blackhole`.

<Note title="What this test does and doesn't prove">

The blackhole cut off zone a's **app** subnet. The data subnets were untouched, so the database kept working. If the database is **Single-AZ**, it lives in one zone. Check which: **Aurora and RDS → Databases → quickcart-db → Connectivity & security → Availability Zone**. If that zone failed for real, the database would go with it, and the site couldn't take orders however many app servers survived. So state your result exactly: *"The app tier survives the loss of a zone with N failed requests. The data tier is Single-AZ and does not."* A precise statement of a limit is worth far more than a result presented as broader than it was.

</Note>

</Step>

<Step title="Test 4: the database restarts">

With a new probe running (`test4.csv`):

<ConsolePath path="Aurora and RDS > Databases > quickcart-db > Actions > Reboot" />

If you built **Multi-AZ**, tick **Reboot with failover**, which makes RDS switch to the standby in the other zone: a real failover test. On Single-AZ that option doesn't exist, and a plain reboot tests something narrower but still important: whether the app **reconnects by itself** when the database comes back.

**What to expect:** the main page fails for somewhere around one to two minutes, then recovers with nobody touching anything, because the app opens a fresh connection for every request. `/health` stays 200 throughout, which is exactly why it doesn't check the database.

</Step>

</Steps>

## Troubleshooting

Every one of these happened in a real build of this environment.

<Mistake title="servers launch, fail, and get replaced, over and over">

The target group shows servers cycling between **initial** and **unhealthy**. **Activity** on the auto scaling group shows a steady stream of launches and terminations, and the bill climbs.

```output title="The target's health status says"
Health checks failed
```

**Why:** the app never started, so `/health` never answered. There are three usual causes:

- `quickcart-app-sg` has **no outbound rule**. `dnf install` hangs without an error, and nothing after it runs.
- The **grace period** is shorter than the boot. Servers are judged before the app has started, and killed.
- The boot script failed partway, for example because `aws s3 cp` was refused.

**The fix:** read the boot log. It's in **CloudWatch → Log groups → /quickcart/bootstrap**, if the agent got that far. If not, use **EC2 → Instances → the instance → Actions → Monitor and troubleshoot → Get system log**, which always works. With `set -x`, the last command printed is the one that failed or hung. While you fix it, you can set the group's desired capacity to `0` to stop the loop.

</Mistake>

<Mistake title="database_unavailable meant two different things">

The page said `database_unavailable` both times. Only the log, in **CloudWatch → Log groups → /quickcart/app**, told the two apart.

```output title="First time: the security group rule was missing"
{"level": "ERROR", "route": "/", "status": 500, "latency_ms": 3004, "error_type": "OperationalError", "message": "(2003, \"Can't connect to MySQL server on 'quickcart-db.abcdefghijkl.us-east-1.rds.amazonaws.com' (timed out)\")"}
```

```output title="Second time: the table didn't exist yet"
{"level": "ERROR", "route": "/", "status": 500, "latency_ms": 41, "error_type": "ProgrammingError", "message": "(1146, \"Table 'quickcart.orders' doesn't exist\")"}
```

**Why:** the page hides the details, as it should. But the log keeps them. The **latency** is a clue on its own: about 3,000 ms is the connect timeout, which means packets were dropped by a firewall. A fast failure means the database answered and said no.

**The fix:** always check `error_type` and `message` in the log before changing anything. A timeout points at security groups and routes. A fast error points at the database itself.

</Mistake>

<Mistake title="Unknown database">

```output title="The app log shows"
{"level": "ERROR", "error_type": "OperationalError", "message": "(1049, \"Unknown database 'quickcart'\")"}
```

**Why:** **Initial database name** was left empty under **Additional configuration** when the database was created, and the seeding script hasn't run yet. The server exists, but there's no database called `quickcart` inside it.

**The fix:** run stage 10's `python3 /opt/app/seed.py`. It creates the database if it's missing, then the tables.

</Mistake>

<Mistake title="the alarm went red, but no email came">

**Why:** the email subscription is still **Pending confirmation**. Unconfirmed subscriptions silently drop everything. This is the most common reason people say their alarms "don't work".

**The fix:** **SNS → Topics → quickcart-alerts → Subscriptions**. If it says **Pending confirmation**, find the confirmation email (check spam), or choose **Request confirmation** to send another.

</Mistake>

<Mistake title="an alarm stays in Insufficient data">

**Why:** the metric has no data points. That's normal for counts when nothing has gone wrong, and the default treatment of missing data leaves the alarm undecided.

**The fix:** edit the alarm and set **Treat missing data as** to **not breaching** for the error counts, as in the table in stage 11.

</Mistake>

<Mistake title="targets are unhealthy with a 404">

```output title="The target's health status details say"
Health checks failed with these codes: [404]
```

**Why:** the health check path doesn't exist in the app. Usually a typo, or `/` instead of `/health`, or a trailing space.

**The fix:** **Target groups → quickcart-tg → Health checks → Edit**, and set the path to exactly `/health`.

</Mistake>

<Mistake title="the browser warns about the certificate">

On path A, when opening the load balancer's own DNS name:

```output title="The browser says something like"
Your connection is not private
NET::ERR_CERT_COMMON_NAME_INVALID
```

**Why:** the certificate is for `shop.example.com`, but the address bar says `quickcart-alb-….elb.amazonaws.com`. Encryption works; the **name** doesn't match.

**The fix:** use the name the certificate is for, through the Route 53 alias record. On path B, a warning is expected for any name, because nothing trusted signed the certificate; that's the trade-off you chose, so use `curl -k` for tests.

</Mistake>

<Mistake title="plain HTTP shows the site instead of redirecting">

**Why:** the HTTP:80 listener was set to **Forward** to the target group, not **Redirect**. Plain, unencrypted traffic then reaches the servers, and the HTTPS setup is decoration.

**The fix:** **Load balancers → quickcart-alb → Listeners and rules → HTTP:80 → Edit listener**: default action **Redirect to URL**, HTTPS, port 443, status 301.

</Mistake>
