QuickCart is about to leave its single server behind. Before any new server, load balancer or database can move in, it needs a network: one where customers can reach the front door, servers can reach the internet and AWS, and nothing outside can ever reach the database.

In this project you build that network by hand, one piece at a time, in the AWS console. No wizard fills anything in for you. At the end you'll prove each piece works from inside the network, with real commands and real answers.

| Flow logs | 1 | A record of every connection accepted or rejected in the VPC |

## Stage 2: Six subnets

A subnet is a slice of the VPC that lives in exactly one availability zone. Surviving the loss of a zone means having a copy of each tier in a second zone, so three tiers become six subnets.

The numbering lets you read a subnet's job from its address: 1 and 2 are public, 11 and 12 are app, 21 and 22 are data. The gaps leave room to grow.

<Steps>

| Subnet name | Availability Zone | IPv4 subnet CIDR block |
|---|---|---|
| `quickcart-public-a` | US East (N. Virginia) / us-east-1a | `10.0.1.0/24` |
| `quickcart-public-b` | US East (N. Virginia) / us-east-1b | `10.0.2.0/24` |
| `quickcart-app-a` | US East (N. Virginia) / us-east-1a | `10.0.11.0/24` |
| `quickcart-app-b` | US East (N. Virginia) / us-east-1b | `10.0.12.0/24` |
| `quickcart-data-a` | US East (N. Virginia) / us-east-1a | `10.0.21.0/24` |
| `quickcart-data-b` | US East (N. Virginia) / us-east-1b | `10.0.22.0/24` |

Leave **IPv4 VPC CIDR block** as `10.0.0.0/16`. Choose **Create subnet**.

## Stage 4: The NAT gateway

Servers in the app subnets must never be reachable from the internet, but they still need to reach out: to install packages when they boot, for example. A NAT gateway is that one-way door.

It goes in a **public** subnet, which feels backwards. It serves the private subnets, but it needs its own route to the internet gateway, and only a public subnet has one.

<Steps>

<Step title="Create the NAT gateway, with an Elastic IP">

<ConsolePath path="VPC > NAT gateways > Create NAT gateway" />

| Field | Enter |
|---|---|
| Name | `quickcart-nat-a` |
| Subnet | `quickcart-public-a` |
| Connectivity type | **Public** |
| Elastic IP allocation ID | Choose **Allocate Elastic IP**. A new address is filled in |

If your console also asks for an **Availability mode**, choose **Zonal**. This project deliberately builds the classic NAT gateway, which lives in one zone, so you can see the zone dependency it creates.

Choose **Create NAT gateway**. It takes two or three minutes to become available.

</Step>

<Step title="Understand the trade-off you just made">

One NAT gateway, in zone a, serves both zones. That halves its cost, but zone b's servers now depend on zone a for their way out to the internet. If zone a fails, they lose it.

Stage 7 softens this: the endpoints give both zones a private path to the AWS services they need, without the NAT. The fully resilient design has **one NAT gateway per zone**, each app subnet using the one in its own zone, for about $1.10 more a day. Write this trade-off down now. You'll see it for yourself in Project 2's zone failure test.

</Step>

</Steps>

**Checkpoint**

<See>

`quickcart-nat-a` with **State: Available**, **Connectivity type: Public**, and a **Primary public IPv4 address**. Write that address down. You'll see it again in *Prove it*.

</See>

## Stage 5: Route tables

This is the stage that decides which subnets are public. Before it, every subnet uses the VPC's **main** route table, which has only the `local` route, so every subnet is isolated.

You'll build four tables. Every table also gets `10.0.0.0/16 → local`, which AWS adds and you can't remove.

| Route table | Its one extra route | Subnets | So the subnets are |
|---|---|---|---|
| `quickcart-rt-public` | `0.0.0.0/0 → quickcart-igw` | public-a, public-b | **Public** |
| `quickcart-rt-app-a` | `0.0.0.0/0 → quickcart-nat-a` | app-a | **Private**: out only |
| `quickcart-rt-app-b` | `0.0.0.0/0 → quickcart-nat-a` | app-b | **Private**: out only, through zone a |
| `quickcart-rt-data` | none | data-a, data-b | **Isolated**: no way in or out |

The two app tables say the same thing today. Keeping them separate makes the cross-zone dependency visible, and adding a second NAT gateway later becomes a one-line change.

<Steps>

<Step title="The public route table">

<ConsolePath path="VPC > Route tables > Create route table" />

| Field | Enter |
|---|---|
| Name | `quickcart-rt-public` |
| VPC | `quickcart-vpc` |

Choose **Create route table**. On its **Routes** tab, choose **Edit routes**, then **Add route**:

| Destination | Target |
|---|---|
| `0.0.0.0/0` | **Internet Gateway**, then `quickcart-igw` |

Choose **Save changes**. On the **Subnet associations** tab, choose **Edit subnet associations**, tick `quickcart-public-a` and `quickcart-public-b`, and choose **Save associations**.

</Step>

<Step title="The two app route tables">

Create two more route tables in the same way, in `quickcart-vpc`:

| Name | Route to add | Associate with |
|---|---|---|
| `quickcart-rt-app-a` | `0.0.0.0/0` → **NAT Gateway** → `quickcart-nat-a` | `quickcart-app-a` |
| `quickcart-rt-app-b` | `0.0.0.0/0` → **NAT Gateway** → `quickcart-nat-a` | `quickcart-app-b` |

</Step>

<Step title="The data route table, with no routes added">

| Field | Enter |
|---|---|
| Name | `quickcart-rt-data` |
| VPC | `quickcart-vpc` |

Add **no** routes. Associate it with `quickcart-data-a` and `quickcart-data-b`.

An empty table is a security control. The database has no reason to reach the internet. With no route out, even a compromised database couldn't send data anywhere or download anything.

</Step>

<Step title="Check the main route table is harmless">

<ConsolePath path="VPC > Route tables" />

Find the table in `quickcart-vpc` that shows **Main: Yes**. It should have only the `local` route and no explicit subnet associations.

Any subnet you forget to associate falls back to the main table. Keeping it local-only means a forgotten subnet has *too little* access, which you notice in minutes, rather than too much, which you might never notice.

</Step>

</Steps>

**Checkpoint**

<See>

On **Subnets**, open each subnet's **Route table** tab. public-a and public-b show `quickcart-rt-public`; app-a shows `quickcart-rt-app-a`; app-b shows `quickcart-rt-app-b`; data-a and data-b show `quickcart-rt-data`. None shows the main table.

</See>

## Stage 6: Security groups

A route table decides whether traffic **can** arrive. A security group decides whether it's **allowed** when it does. You'll build four, as a chain: each one names the group before it as its source, never a range of addresses.

| Group | Inbound | From | Why |
|---|---|---|---|
| `quickcart-alb-sg` | HTTPS 443, HTTP 80 | `0.0.0.0/0`, anywhere | The load balancer is the only thing customers talk to. Port 80 is only there to redirect to HTTPS |
| `quickcart-app-sg` | HTTP 80 | `quickcart-alb-sg` | Only the load balancer can reach the app servers |
| `quickcart-db-sg` | MySQL 3306 | `quickcart-app-sg` | Only app servers can reach the database |
| `quickcart-endpoints-sg` | HTTPS 443 | `quickcart-app-sg` | Only app servers can use the interface endpoints |

Naming a group means "anything wearing that group". When a server is replaced and gets a new address, nothing needs updating.

<Steps>

<Step title="The load balancer's group">

<ConsolePath path="VPC > Security groups > Create security group" />

| Field | Enter |
|---|---|
| Security group name | `quickcart-alb-sg` |
| Description | `Load balancer: HTTPS and HTTP from anywhere` |
| VPC | `quickcart-vpc` |

Under **Inbound rules**, choose **Add rule** twice:

| Type | Source |
|---|---|
| **HTTPS** | **Anywhere-IPv4** (`0.0.0.0/0`) |
| **HTTP** | **Anywhere-IPv4** (`0.0.0.0/0`) |

Leave **Outbound rules** as they are: **All traffic** to `0.0.0.0/0`. Choose **Create security group**.

</Step>

<Step title="The app servers' group">

| Field | Enter |
|---|---|
| Security group name | `quickcart-app-sg` |
| Description | `App servers: HTTP from the load balancer only` |
| VPC | `quickcart-vpc` |

One inbound rule:

| Type | Source |
|---|---|
| **HTTP** | **Custom**, then start typing `quickcart-alb-sg` and choose the **group**, not an address range |

**Leave the outbound rule in place: All traffic to `0.0.0.0/0`.** Security groups are stateful, so replies to incoming requests go back out on their own. But connections the server **starts** need an outbound rule, and a booting server does little else: it registers with Systems Manager, fetches its secret and downloads packages. Choose **Create security group**.

There's no SSH rule, on purpose. You'll reach servers through Session Manager, which needs no open inbound port at all.

</Step>

<Step title="The database's group">

Choose **Create security group**.

## Stage 7: VPC endpoints

App servers need S3, Secrets Manager and Systems Manager. Without endpoints, those requests go out through the NAT gateway to AWS's public addresses. Endpoints keep them inside AWS's network, and keep them working if the NAT gateway or its zone fails.

| Kind | How it works | Cost |
|---|---|---|
| **Gateway endpoint** (S3) | Adds a route to your route tables. S3's addresses go to the endpoint instead of the NAT gateway | Free |
| **Interface endpoint** (everything else) | Puts a network interface with a private address in your subnets, and makes the service's normal name resolve to it | About $0.01 an hour per zone, each |

<Steps>

<Step title="The S3 gateway endpoint">

<ConsolePath path="VPC > Endpoints > Create endpoint" />

| Field | Enter |
|---|---|
| Name tag | `quickcart-ep-s3` |
| Type | **AWS services** |
| Services | Search for `s3`, and choose `com.amazonaws.us-east-1.s3` with **Type: Gateway**. There's also an **Interface** one with the same name; not that one |
| VPC | `quickcart-vpc` |
| Route tables | Tick `quickcart-rt-app-a` and `quickcart-rt-app-b` |
| Policy | **Full access** |

Choose **Create endpoint**.

</Step>

<Step title="Four interface endpoints">

Create four more endpoints on the same form. Everything is the same except the name and the service:

| Name tag | Service (Type: Interface) | What it's for |
|---|---|---|
| `quickcart-ep-secretsmanager` | `com.amazonaws.us-east-1.secretsmanager` | Reading the database password |
| `quickcart-ep-ssm` | `com.amazonaws.us-east-1.ssm` | Systems Manager itself. Without it, Session Manager can't start |
| `quickcart-ep-ssmmessages` | `com.amazonaws.us-east-1.ssmmessages` | The channel a Session Manager shell runs over. Without it, a session connects and then hangs |
| `quickcart-ep-ec2messages` | `com.amazonaws.us-east-1.ec2messages` | The agent's command channel. Without it, the server may never show up as managed |

For each one:

| Field | Enter |
|---|---|
| Type | **AWS services** |
| VPC | `quickcart-vpc` |
| Additional settings → Enable DNS name | **Ticked**. This is the whole point: see below |
| DNS record IP type | **IPv4** |
| Subnets | us-east-1a → `quickcart-app-a`; us-east-1b → `quickcart-app-b` |
| IP address type | **IPv4** |
| Security groups | `quickcart-endpoints-sg` only. Untick the VPC's default group |
| Policy | **Full access** |

**Why the DNS setting matters.** With it ticked, the normal name `secretsmanager.us-east-1.amazonaws.com` resolves to the endpoint's private address inside your subnet. Your code doesn't change at all. With it unticked, the name still resolves to a public address, traffic still goes through the NAT gateway, and the endpoint sits there billing you.

**The fix:** do stage 1's **Edit VPC settings** step, then create the endpoint again.

</Mistake>

</Step>

## Stage 9: Least-privilege IAM roles

A server that calls AWS needs permission. Access keys on the server are how credentials leak. Instead, the server wears an **IAM role**: AWS hands it short-lived credentials that change on their own, and nothing is stored on disk.

**Least privilege** means each role can do exactly its job. The app role can read **one** secret and **one** bucket, not every secret and every bucket.

<Steps>

<Step title="Create the app servers' role">

<ConsolePath path="IAM > Roles > Create role" />

| Field | Enter |
|---|---|
| Trusted entity type | **AWS service** |
| Service or use case | **EC2** |
| Use case | **EC2** |

Choose **Next**. Search for and tick these two AWS managed policies:

| Policy | What it allows |
|---|---|
| `AmazonSSMManagedInstanceCore` | Registering with Systems Manager, so you can use Session Manager with no SSH |
| `CloudWatchAgentServerPolicy` | Sending logs and metrics to CloudWatch. Project 2 uses it |

Choose **Next**.

| Field | Enter |
|---|---|
| Role name | `quickcart-app-role` |
| Description | `QuickCart app servers: SSM, CloudWatch, one secret, one bucket` |

Choose **Create role**.

</Step>

<Step title="Add a policy for exactly one secret">

<ConsolePath path="IAM > Roles > quickcart-app-role > Add permissions > Create inline policy" />

Choose **JSON**, delete what's there, and paste this. Put your own account ID in place of the highlighted number:

```json title="quickcart-read-secret" ph="111122223333"
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadTheTestSecret",
      "Effect": "Allow",
      "Action": "secretsmanager:GetSecretValue",
      "Resource": "arn:aws:secretsmanager:us-east-1:111122223333:secret:quickcart/test-*"
    }
  ]
}
```

| Part | What it means |
|---|---|
| `"Version": "2012-10-17"` | The policy language version. Always this date; it isn't when you wrote it |
| `"Sid"` | A label for this statement, for people reading it |
| `"Effect": "Allow"` | This statement grants permission. Anything not allowed is denied |
| `"Action": "secretsmanager:GetSecretValue"` | Only reading a secret's value. Not listing secrets, changing them or deleting them |
| `"Resource"` | Only this secret. The `-*` at the end matches the six random characters AWS adds to every secret's ARN. Without it, the policy matches nothing |

Choose **Next**, name it `quickcart-read-secret`, and choose **Create policy**.

</Step>

<Step title="Add a policy for exactly one bucket">

Create a second inline policy in the same way:

```json title="quickcart-read-assets" ph="111122223333"
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadObjects",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::quickcart-assets-111122223333/*"
    },
    {
      "Sid": "ListTheBucket",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::quickcart-assets-111122223333"
    }
  ]
}
```

| Part | What it means |
|---|---|
| `s3:GetObject` on `…/*` | Read any **object** (file) in the bucket. Objects are addressed as bucket name, a slash, then the object's key, hence `/*` |
| `s3:ListBucket` on the bucket's ARN | List what's **in** the bucket. This action acts on the bucket itself, so its ARN has no `/*` |

Name it `quickcart-read-assets` and choose **Create policy**. Mixing up the two ARNs is one of the most common IAM mistakes there is: see *Troubleshooting*.

</Step>

<Step title="Create the flow logs' log group">

Flow logs need somewhere to write. Create the log group first, so the role can be limited to exactly it.

<ConsolePath path="CloudWatch > Log groups > Create log group" />

| Field | Enter |
|---|---|
| Log group name | `/quickcart/vpc-flow-logs` |
| Retention setting | **1 week**. Logs kept forever cost money forever |
| Log class | **Standard** |

Choose **Create**.

</Step>

<Step title="Create the flow logs' role">

This role is used by the VPC Flow Logs service, not by a server, so it needs a custom trust policy.

<ConsolePath path="IAM > Roles > Create role" />

For **Trusted entity type**, choose **Custom trust policy**, and paste:

```json title="Trust policy" ph="111122223333"
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "vpc-flow-logs.amazonaws.com" },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": { "aws:SourceAccount": "111122223333" }
      }
    }
  ]
}
```

| Part | What it means |
|---|---|
| `"Principal": { "Service": "vpc-flow-logs.amazonaws.com" }` | Only the VPC Flow Logs service may use this role |
| `"Action": "sts:AssumeRole"` | "Use" means taking on the role's permissions for a while |
| `"Condition"` → `"aws:SourceAccount"` | And only when it's acting for **your** account. This stops another account's flow logs being pointed at your role |

Choose **Next**, add no managed policies, choose **Next**, name it `quickcart-flow-logs-role`, and choose **Create role**. Then add this inline policy to it, named `quickcart-write-flow-logs`:

```json title="quickcart-write-flow-logs" ph="111122223333"
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "WriteToOneLogGroup",
      "Effect": "Allow",
      "Action": [
        "logs:CreateLogStream",
        "logs:PutLogEvents",
        "logs:DescribeLogStreams"
      ],
      "Resource": "arn:aws:logs:us-east-1:111122223333:log-group:/quickcart/vpc-flow-logs:*"
    },
    {
      "Sid": "FindTheLogGroup",
      "Effect": "Allow",
      "Action": "logs:DescribeLogGroups",
      "Resource": "*"
    }
  ]
}
```

| Part | What it means |
|---|---|
| `logs:CreateLogStream`, `logs:PutLogEvents` | Create a stream inside the group, and write records to it |
| `logs:DescribeLogStreams` | See which streams already exist |
| Resource ending `log-group:/quickcart/vpc-flow-logs:*` | Only this one log group, and the streams inside it |
| `logs:DescribeLogGroups` on `*` | List the names of log groups, to find this one. It can't read or change any of them |

</Step>

## Troubleshooting

These are real mistakes from building exactly this network.

<Mistake title="everything on the server times out, and Session Manager won't connect">

The server starts, but **Connect** says the agent isn't online. With no shell, you can't look inside. **EC2 → Instances → quickcart-test → Actions → Monitor and troubleshoot → Get system log** shows the boot output, with lines like:

```output title="The system log shows lines like"
Failed to connect to ssm.us-east-1.amazonaws.com port 443 after 130000 ms: Connection timed out
```

**Why:** `quickcart-app-sg` has **no outbound rule**. It's easy to assume that because security groups are stateful, outbound is taken care of. Only **replies** are. Every connection the server starts, to the SSM endpoints, to Secrets Manager, to package mirrors, needs an outbound rule, and a timeout is what a dropped packet looks like.

**The fix:** add the outbound rule back to `quickcart-app-sg`: **All traffic** to `0.0.0.0/0`. The agent connects within a minute or two. The **Get system log** trick is worth remembering: it works even when nothing else can reach the server.

</Mistake>

<Mistake title="Session Manager connects, then the shell never appears">

The browser tab opens and stays blank, or shows only a spinner.

**Why:** the `ssmmessages` endpoint is missing, or it's using the VPC's default security group. Registration uses `ssm` and `ec2messages`, but the shell itself runs over `ssmmessages`.

**The fix:** check that `quickcart-ep-ssmmessages` exists, is **Available**, is in both app subnets, and has `quickcart-endpoints-sg`. To change an endpoint's group: **VPC → Endpoints → the endpoint → Actions → Manage security groups**.

</Mistake>

<Mistake title="reading a file from S3 says Forbidden, with no reason">

```output title="aws s3 cp fails with"
fatal error: An error occurred (403) when calling the HeadObject operation: Forbidden
```

**Why:** `s3:GetObject` was granted on `arn:aws:s3:::quickcart-assets-111122223333`, the **bucket**, instead of `arn:aws:s3:::quickcart-assets-111122223333/*`, the **objects in it**. The CLI checks the file first with a `HeadObject` request, which S3 refuses without saying why.

**The fix:** make sure the `GetObject` statement's resource ends in `/*`, and the `ListBucket` statement's doesn't.

</Mistake>

<Mistake title="the role can't read its own secret">

```output title="get-secret-value fails with"
An error occurred (AccessDeniedException) when calling the GetSecretValue operation: User: arn:aws:sts::111122223333:assumed-role/quickcart-app-role/i-0a1b2c3d is not authorized to perform: secretsmanager:GetSecretValue on resource: quickcart/test because no identity-based policy allows the secretsmanager:GetSecretValue action
```

**Why:** the policy's resource ends in `secret:quickcart/test` with no `-*`. Every secret's real ARN has six random characters on the end, so the policy matches nothing.

**The fix:** end the resource with `quickcart/test-*`, or paste the secret's full ARN from its page.

</Mistake>

<Mistake title="the secret request hangs instead of failing">

The `get-secret-value` command sits there for a minute or more, then fails with a message about the endpoint URL or a timeout.

**Why:** the interface endpoints are still using the VPC's **default** security group, which only allows traffic from itself. Nothing from `quickcart-app-sg` gets in, and dropped traffic looks like silence.

**The fix:** swap each interface endpoint's group to `quickcart-endpoints-sg`, as in *the shell never appears* above.

</Mistake>

<Mistake title="curl to checkip hangs">

`curl -s checkip.amazonaws.com` prints nothing for a long time.

**Why:** usually one of three things. The NAT gateway was created in a **private** subnet, so it has no route to the internet itself. Its **Connectivity type** is **Private**. Or `quickcart-app-a` is still using the main route table, which has no `0.0.0.0/0` route.

**The fix:** check the app subnet's **Route table** tab first. If that's right, open the NAT gateway and check its **Subnet** is `quickcart-public-a` and its type is **Public**. A NAT gateway can't be moved; delete it and create it again in the right place.

</Mistake>

<Mistake title="the bill still shows an Elastic IP after clean-up">

**Why:** deleting a NAT gateway doesn't release its Elastic IP. An address that isn't released keeps costing about $0.005 an hour, even attached to nothing.

**The fix:** **VPC → Elastic IPs → the address → Actions → Release Elastic IP addresses**. The clean-up below includes it.

</Mistake>
